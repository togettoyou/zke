# Phase 4 AIOps 架构

> 状态：模型端点配置、会话与 append-only 轨迹存储、后台运行、SSE 续传与流式增量、权限重验、可重建摘要压缩、
> 模型自主工具循环、受控资源写操作、敏感工具审批等待、证据引用，以及 AIOps App 的会话、对话/轨迹 Tab、
> 轨迹时间线与详情、文本附件、搜索、归档、删除和导出，受控 Cluster Terminal 命令，以及随 Server 发布的排查
> 技能与只读并行子任务已经落地；定时巡检与事件触发自动化仍在规划中。

AIOps 是运行在 ZKE 云端的 Codex 式运维应用。它跟随 Console 桌面环境当前选定的 Tenant 和 Project，并在创建会话时
选定该 Project 下的一个 Cluster。它的目标是让用户用自然语言完成该集群的巡检、故障分析、
资源读写、应用部署、指标查询和终端操作；任务可以在窗口关闭后继续。与编码助手相比，AIOps 的工作对象不是本地
目录，而是 ZKE 已接入且当前用户有权访问的 Kubernetes 资源。当前实现提供模型自主工具循环、敏感工具审批、
显式证据引用、工作负载伸缩/回滚、Manifest DryRun/差异/Apply/Delete、受控 Cluster Terminal 命令，以及随 Server
发布的排查技能与只读并行子任务。

它额外提供“轨迹”：对模型、上下文、工具调用、审批、压缩和结果的完整时间线，既用于实时观察，也用于事后复盘。
并行子任务的每一步也写在同一条轨迹里并带分支标记，因此“主线做了什么”和“某个分支报告了什么”始终能分开读。

## 产品形态

AIOps 作为独立 App 使用会话侧栏加主工作区：

- 左侧选择 Cluster 工作区，并展示该 Cluster 的会话、搜索和归档；
- 主工作区顶部使用“对话 / 轨迹”Tab；对话展示运行阶段、结论和证据；
- 轨迹展示按来源筛选和搜索的事件列表、运行汇总与单条详情，会话可整体导出；
- 输入区提供文本附件、发送和停止；
- 会话可继续、重命名、归档，已归档会话可永久删除；运行中的任务关闭窗口后继续，可重新打开或取消；
- 计划支持定时巡检、告警触发取证和其他自动化，但必须使用显式委派，不能借用过期的浏览器 Session。

界面借鉴 Codex 的交互，不复制其品牌、图标或文案。AIOps 不是旁挂聊天框，也不是只会给建议的 Copilot。

## 桌面作用域与会话 Cluster

AIOps 不提供 Global、Tenant 或 Project 选择器。它与容器服务一样，直接使用 Console 桌面环境当前选定的 Tenant 和
Project，并在 App 内选择一个 Cluster 作为工作区。会话列表和搜索同时按 Tenant、Project、Cluster 隔离；切换 Cluster
只显示新工作区中的会话，新建会话也固定到当前 Cluster。

创建会话时必须从当前 Project 中选定一个在线 Cluster。`tenant_id`、`project_id` 和 `cluster_id` 都持久化到会话且
创建后不可切换；三者不使用数据库外键，以保留作用域删除后的会话记录，API 每次访问仍会重新解析并校验当前归属和权限。
一个会话不做跨 Cluster 查询、证据拼接或操作。Cluster 只确定资源目标，不新增 Cluster 级 RoleBinding，授权仍只有
ZKE 既有的 Global、Tenant 和 Project 三层。

当前证据引用和未来的每次工具调用都必须同时满足：

1. 目标严格等于会话固定的 Cluster；
2. 用户当前仍持有该操作所需的 ZKE 权限；
3. 写操作满足届时生效的审批模式；
4. Cluster、Namespace 和资源身份明确。

未来的每次查询、部署和命令执行都只能由该会话 Cluster 的 Agent 执行。AIOps 不让 Server 持有 kubeconfig，也不要求
Server 直连 Kubernetes API Server。

## 身份与后台运行

交互任务以发起用户为主体。会话范围不超过创建时的 Project、固定 Cluster 和用户当时持有的权限；
每次工具调用还要重新检查账户状态与当前 RBAC。关闭浏览器或窗口不终止任务，停用账户、撤销权限、删除 Project 或 Cluster
或用户主动取消会立即阻止后续调用。

自动化不能长期冒用自然人的在线 Session。定时或事件触发任务需要独立的委派记录，明确所有者、Project、Cluster、允许的
权限、审批策略、有效期和撤销状态。审计同时记录委派所有者、实际运行和目标资源。该机制落地前不开放无人值守写操作。

`ai.run` 是使用 AIOps 的前置权限，不放大任何集群权限。内置只读角色不默认获得它，因为模型调用会把经授权的
集群内容发送到管理员配置的端点并消耗共享资源。

## Codex 式工具

模型自主选择工具，Server 维护目录。一个 Turn 由多个 Step 组成：一次模型调用加上它请求的工具执行，工具结果进入
下一个 Step，循环在模型不再请求任何工具时结束。目录不可由会话或模型扩展——它承载的是 Server + Agent、RBAC、
单 Cluster 定域、审批、幂等和审计这些必须长期成立的约束，做成可插拔就等于把安全边界做成可插拔。

已实现的只读工具：Cluster 概览、API 资源目录、对象列表与详情、对象诊断（含指向它的 Event）、Node 列表、
Pod 日志（敏感）、指标查询目录与查询执行。每个工具声明自己需要的权限集合，运行时在每次调用前逐项重验；
参数按 Schema 解码，未声明字段一律拒绝；目标 Cluster 由运行时填入，模型无法在参数里改写。完整目录与权限对照见
[AIOps](../features/ai-assistant.md)。

资源写操作把预检和提交拆成不同工具：伸缩使用同参数 DryRun；Manifest Apply/Delete 与工作负载回滚在预检后返回
`preview_id`，Server 保存原始目标与内容，实际提交不再接受可替换的 YAML 或回滚参数。批准后会重新解析当前 RBAC、
重新 DryRun，再沿用既有显式确认和 Agent 幂等路径提交。Manifest 按每个文档实际动作选择 create/update/delete、
Namespace、RBAC 或受保护 Namespace 权限；回滚按普通、系统或 Agent Namespace 选择有效权限。包含写工具的同一步
调用不并发，按模型请求顺序执行。AIOps 拒绝 Secret 清单，避免 Secret 明文进入模型上下文和轨迹。

受控 Cluster Terminal 命令已经实现：`run_terminal_command` 在目标 Agent 创建的 Turn 级终端 Pod 中执行非交互
Shell 命令，固定要求 `cluster.terminal.exec` 并标记为敏感且可能变更。一个 Turn 的首次命令批准后重新计算用户当前
Cluster 权限并投射 Kubernetes RBAC，后续命令复用该 Pod 与冻结快照；`kubectl exec` 还需 `cluster.pod.exec`，受保护 Namespace 再叠加对应管理权限；AIOps
仅不投射 Secret 读写权限。命令容器通过 localhost 凭证代理访问 API Server，本身不挂载
ServiceAccount Token。命令和有界输出属于不可信轨迹数据，会发送到模型端点。权限重验覆盖命令之间的空闲期，撤权、
Turn 结束、失败或取消都会关闭 Pod 和临时 RBAC。

技能（Playbook）是 Server 自己发布的流程说明，不是能力。一条技能只能说明用目录里的哪些工具、按什么顺序取证、
以什么标准下结论；它不携带权限、不新增工具、不改变审批模式，也不能指定另一个 Cluster。模型在系统提示词里只看到
技能 ID 和一句话摘要，需要时用 `load_skill` 读取正文——这是目录里唯一一个答复不来自 Cluster 的工具，因此也是唯一
被标记为可信的工具结果。技能随代码发布而不是由会话或租户编写：技能正文是给模型遵循的指令，一段集群或用户能写入
的技能就是 Phase 4 其余部分一直在拒绝的提示注入。所需工具没有全部组装的技能不会出现在目录里，而不是出现后在
第三步失败。

并行子任务用于互不依赖的取证分支。`run_subtasks` 由主 Agent 调用，每个分支是一次独立的只读调查：只拿到目标和主
Agent 显式传递的少量已知信息，看不到对话也看不到彼此，只有只读工具，不能再派生子任务，各自持有独立的 Step、
工具调用与超时预算。分支的每一步写进同一条会话轨迹并带分支标记，结论、证据与失败分类汇总成主线的一条工具结果，
冲突由主 Agent 消解。父 Turn 结束前一定回收全部分支——它们在这次工具调用内被等待，不存在跨 Turn 存活的分支。
写操作不参与派发：写入的顺序、幂等与审批保证定义在一条串行路径上，没有一种“多个 Agent 同时 Apply”能保住它们。

仍在规划的工具：

- Pod Exec、日志流和临时访问；
- Cluster Terminal 的受控交互会话；
- 会话计划与产物。

写工具必须走 ZKE 已有服务层的授权、幂等、超时和审计路径，不能绕开 Agent、RBAC 或敏感操作保护。终端工具通过目标
集群 Agent 创建短生命周期 Cluster Terminal，不在 Server 主机执行，也不给模型 kubeconfig。

## 审批模式

与 Codex 同类的三档模式：

| 模式 | 行为 |
| --- | --- |
| 请求批准（默认） | 写工具和敏感工具逐次等待用户确认 |
| 帮我批准 | 只有敏感工具等待确认——沿用 ZKE 已有的敏感操作定义：删除、Secret、RBAC、节点排空、受保护 Namespace、Pod 日志 |
| 完全访问 | 在会话固定 Cluster 和用户当前权限内自动执行，不跳过授权、DryRun、幂等或审计 |

审批请求展示目标 Cluster/Namespace、具体工具与参数。模式变化和每次批准/拒绝都写入轨迹，因此记录能说明每一段
运行在哪个模式下。拒绝不是运行失败：模型收到明确的拒绝说明并在不执行它的前提下继续；无人答复超时才结束本轮。

三档都不扩大权限，上限始终是发起用户自己的 RBAC。它们真正改变的是一段来自 Pod 日志的提示注入能走多远。
当前敏感读取是 Pod 日志；实际资源写工具使用 `mutating` 标记进入同一审批状态机，删除固定为敏感，RBAC、受保护
Namespace 与强制字段接管按预检快照动态升级为敏感。“请求批准”会逐次等待，“帮我批准”只等待敏感调用，
“完全访问”在当前权限允许时直接执行；DryRun 工具不带写标记，因为它不会改变集群。

## 会话、运行与轨迹

会话长期保存对话；一次用户输入产生一个运行。Server 先持久化轨迹条目，再向 Console 推送，所以断线重连可从
最后序号继续。一个会话同一时刻只运行一个主任务；运行时可以派生有界子任务并行取证，它们的条目写回同一条轨迹并带
分支标记（分支 ID、派发它的工具调用、序号和目标），因此并发写入的多条分支仍然可分、可折叠、可复盘。

轨迹使用固定事件类型：`system`、`input`、`context`、`model`、`reasoning`、`tool_call`、`tool_result`、
`approval_request`、`approval_decision`、`compaction`、`conclusion`、`error`。每项记录序号、轮次、步骤、时间、
耗时和必要的作用域引用；模型项还记录 token 与首 token 时延，工具项还记录调用标识、参数、是否执行和证据。
大正文只保存有界摘录与回链，轨迹不是日志仓库。

会话正文默认保留 30 天，审计按平台策略保留。读取历史时必须重新检查当前 Project 和会话 Cluster 权限：用户自己的问题和系统状态
仍可见，已无权访问的集群正文、工具结果和证据应被服务端脱敏，而不是只靠前端隐藏。

## 模型接入与上下文管理

全局管理员在“平台配置 → AI 模型”配置：

- Base URL、API Key、模型名和 API 协议（Responses 或 Chat Completions）；
- 上下文窗口、单次最大输出和请求超时。

出厂状态是一个预置组合并默认开启：`https://api.deepseek.com`、Responses、`deepseek-v4-flash`，只有 API Key
留空。地址、协议与模型名必须彼此匹配；端点若不在所选协议上应答，连通性测试会先报出来，第一轮也会以
`model_rejected` 结束，而不是含混地报成端点不可用。预置改变的是默认目的地，不改变授权：每一轮仍需要 `ai.run`，
而端点会拒绝没有凭证的请求，所以没有补齐 Key 的部署到不了外发那一步。

这些值不能从“模型名”猜测。自建端点可能使用同名模型但有不同窗口，错误的窗口会导致过早压缩或请求溢出。

**何时压缩不在这里配置**，它是部署策略而不是端点事实：Server 配置文件 `aiops.compaction` 保存的是比例
（`threshold_ratio` 默认 0.8、`retain_ratio` 默认 0.16），乘以上面这个窗口得到触发点与保留尾部。存一个绝对阈值
会在同一部署改指另一个模型的那一刻悄悄失效。

每次模型调用前，运行时估算这次请求的占用：优先锚定端点上一次报告的用量，只对此后新增的条目做本地估算。达到
阈值时压缩，并始终为 `max_output_tokens` 留出空间：

1. 从尾部保留 `retain_ratio × 窗口` 的最近工作，边界推到 Step 开头，不拆开工具调用与它的结果；
2. 之前的区间交给模型写成结构化检查点，摘要调用复用同一套系统指令与工具 Schema 以命中前缀缓存；
3. 检查点必须保留用户目标、约束、已确认事实、已执行读取、未决问题、当前进展、下一步与证据引用；安全指令和授权
   边界不参与替换；
4. 摘要调用失败且重试用尽时退回机械摘要，方法记为 `summary`；
5. 方法、触发原因、前后 token、阈值、保留尾部与**被替换的轨迹序号区间**写入 `compaction`；压缩后仍超限则以
   `budget_exceeded` 明确失败，不静默丢上下文。

端点直接以“请求过大”拒绝时同样按上述流程压缩并重发一次；这是端点的账本与我们的估算不一致时唯一能改变结果的
动作。原始轨迹不被改写。

## 不可信输入与数据外发

Pod 日志、Event、annotation、ConfigMap、镜像输出和终端 stdout 都是数据，不是指令。工具白名单、目标作用域、
审批和权限由 Server 状态决定，不能被这些文本改写。

启用 AIOps 后，用户问题、文本附件、显式引用的证据，以及模型自主调用工具读取到的资源、Event、日志、指标和 Helm
Release 元数据会发送到配置的模型端点。ZKE 自身的 Session Token、Agent 证书、模型 API Key 和 kubeconfig
永不进入模型上下文、轨迹或审计正文。Helm Release 的 values 取值、NOTES.txt 与渲染后的 Manifest 正文同样不进入：
它们是 Release Secret 的内容，工具只返回 Chart 身份、revision、状态、被覆盖的 values 路径与渲染出的对象清单。

## 落地顺序

1. 模型配置、跟随桌面 Tenant/Project 并按 Cluster 隔离的会话与轨迹底座（已实现）；
2. `ai.run`、后台运行、SSE/重连、上下文预算、可重建摘要压缩与证据引用（已实现）；
3. AIOps App：Cluster 工作区、对话/轨迹 Tab、轨迹筛选与详情、文本附件、搜索、归档、删除、导出和证据深链（已实现）；
4. 模型自主工具循环、读取工具目录、敏感工具审批等待、流式输出与轨迹时间线（已实现）；
5. 资源写工具、部署与 Cluster Terminal 非交互命令，复用现有权限、幂等键和敏感操作确认（已实现）；
6. 随 Server 发布的排查技能与只读并行子任务（已实现）；
7. Helm Release 只读接入：与 Console 同一组权限（`cluster.read` + `cluster.secret.read`），只返回 Release 的身份与
   形状，不返回 values 取值、NOTES.txt 与 Manifest 正文（已实现）；
8. 定时巡检与事件触发自动化；
9. 质量评估、配额、反馈和运行治理。

## 非目标

- 不在 Server 主机执行模型生成的 shell；
- 不让 Server 直连集群或保存 kubeconfig；
- 不提供绕过 ZKE RBAC、审批、幂等和审计的 AI 专用写路径；
- 不把 AIOps 描述为无人监督或保证正确；
- 不在 Phase 4 自建通用模型训练平台。

运行循环、上下文表层替换和子 Agent 约束见 [AIOps Agent 运行时与上下文设计](ai-agent-runtime.md)。
