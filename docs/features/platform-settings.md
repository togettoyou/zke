# 平台配置

平台配置保存在 PostgreSQL，只能由全局 `admin` 在 Console 的「平台配置」应用中修改，改完立即生效，不需要重启
Server，也不需要重新部署。它与部署前必须确定的引导配置是两层：引导配置决定 Server 怎么启动，平台配置决定
ZKE 往目标集群里装什么。取值与覆盖方式见[部署指南 · 引导配置](../deployment.md#引导配置)。

## 五页配置

- **端点** —— Agent 接入端点预设：注册 URL、QUIC 地址、可选注册 HTTPS CA；
- **Agent** —— Agent 的镜像、Image Pull Policy 与 CPU / 内存请求与限制；
- **集群终端** —— Cluster Terminal 会话 Pod 的镜像、Image Pull Policy、CPU / 内存请求与限制，以及会话存续
  时长，可选 1 分钟至 1 小时，默认 15 分钟；
- **指标采集** —— 三个采集组件（vmagent、kube-state-metrics、node-exporter）各自的镜像、Image Pull Policy
  与 CPU / 内存请求与限制。三者一并安装，因此版本也在同一页固定，避免一个部署跑着今年的采集组件和去年的
  导出器；
- **AI 模型** —— AIOps 的模型端点、协议、上下文预算、凭证与超时，并可测试连通性。

除端点与 AI 模型外，每一页对应一个 ZKE 装进目标集群的工作负载，六个字段的形状完全相同：镜像、拉取策略和四项
资源数量。
数量留空表示不在容器上设置该项——Kubernetes 没有别的方式表达「不限制」，需要交给 Namespace 的 LimitRange
决定时就留空。

每一页各自保存，只写入本页的改动；离开一页会丢弃其中尚未保存的修改，回到该页看到的始终是当前实际生效的
配置。

## 默认值的取值理由

Agent 默认 `50m` / `128Mi` 请求、`512Mi` 内存限制、**不设 CPU 限制**：请求的作用是让它不再是 BestEffort
Pod——节点内存不足时 BestEffort 最先被驱逐，而 Agent 一挂，该集群在 ZKE 里就整个失联；不设 CPU 限制则是因为
被限流的 Agent 不会报错，只会让该集群的每一次查询、终端按键和日志流都变慢，且任何错误信息里都看不出原因。
这两个数字是让 Pod 可调度、可存活的下限，不是实测用量，实际开销取决于集群规模与被监视的对象数量，投产前
应按自己的部署观察后调整。

Cluster Terminal 默认 `25m` / `64Mi` 请求、`500m` / `256Mi` 限制。内存上限刻意保留余量：终端里的 kubectl
对着大集群取全量 JSON 是其中唯一真正占内存的操作，上限压得太低会让一条正常命令直接被 OOMKill，而现象上完全
看不出是内存限制导致的。

node-exporter 跑在每个节点上，它的预算会乘以集群规模，因此默认值刻意很小（请求 `10m` / `32Mi`，限制
`200m` / `128Mi`）。

## 生效时机

三层不同，改配置前需要知道自己改的是哪一层：

- Cluster Terminal 的镜像、拉取策略、资源预算与会话时长**立即**用于新会话；
- 三个采集组件的取值在**下一次安装**时读取，已安装的集群会在「可观测性 → 采集接入」中提示可以更新；
- Agent 的镜像、拉取策略、资源预算、Namespace 和凭证选中的端点在**新 Enrollment 签发**时进入不可变快照，
  已签发的凭证和已接入的集群不受影响。

平台默认接入端点是唯一的例外：它来自引导配置的 `agent_install` 两项，Server 每次启动都按当前有效配置重新
同步，Console 不能修改、删除或另设平台默认端点。

## AI 模型接入

> 这一页用于配置和测试已经落地的 AIOps 运行时与 App；模型自主工具循环、敏感工具审批、工作负载伸缩/回滚和
> Manifest Apply/Delete 已接入，Cluster Terminal 与配额治理仍在规划中。

AIOps 的模型端点与上下文预算保存在平台配置，改完用于后续新运行。它与前四页的定位
一致：部署前必须确定的进引导配置，运行期可调的进平台配置。

这一页与前四页有两点不同，因此不套用同一组字段：

- 它配置的不是 ZKE 装进目标集群的工作负载，而是 **Server 自己往外拨的一个连接**。模型请求从 Server 出站，
  不经过 Agent，目标集群不需要任何出向能力；
- 它包含一个凭证。API Key 写入后不回显，读取配置的接口只返回「是否已配置」，既不返回明文也不返回密文，
  也不进入日志、审计事件与错误消息。

字段：

| 字段 | 说明 |
| --- | --- |
| 启用开关 | 默认开启；切换时立即调用独立接口生效，不依赖“保存模型接入”，关闭后保留配置。未保存接入地址与模型名之前不可开启 |
| 接入地址 | OpenAI 兼容端点的 Base URL，通常以 `/v1` 结尾 |
| API 协议 | Responses（推荐）或 Chat Completions |
| 模型名 | 由管理员填写，不内置厂商模型清单 |
| API Key | 只写不读；无需凭证的内网服务可留空 |
| 上下文窗口 | 模型真实总窗口，例如 262144 或 1000000 tokens |
| 单次最大输出 | 为回答、工具调用和推理预留的空间，必须小于上下文窗口 |
| 请求超时 | 单次模型调用上限，5 至 300 秒 |

上下文窗口不能按模型名猜测：同名自建模型可能使用不同配置。填写错误会导致过早压缩或请求超过端点上限。

何时压缩不在这里配置。它是 Server 配置文件 `aiops.compaction` 里的**比例**（默认窗口的 80%），乘以上面这个窗口
得到触发点，因此换模型只需要改这一页，不必再同步维护一个绝对的 token 阈值。

**连通性测试**按所选协议用已保存的配置发起一次最小请求，只返回成功或分类后的失败原因——认证失败、模型或
路径不存在、连接失败、超时、响应异常——不回显凭证内容，也不回显端点返回的正文。测试不要求配置处于启用状态：
先配置、再测试、最后启用是操作者的自然顺序。测试读取的是**已保存**的配置，因此表单有未保存的修改时它不可用。

启用开关与模型配置保存相互独立：保存按钮只更新端点、模型、凭证和预算，开关每次变化都立即提交并单独增加修订号。
ZKE 预置一个组合并默认开启：接入地址 `https://api.deepseek.com`、协议 Responses、模型 `deepseek-v4-flash`，
只有 API Key 留空。这样新部署只需要补一个字段，而不必先自行确定端点、协议、模型名和两个 token 预算。填好 Key
后先点一次**连通性测试**：协议选错会在这里就报出来，而不是等到第一次提问。

预置不代表数据已经在外发：每一轮仍需要用户在某个 Cluster 上持有 `ai.run`，而默认端点会拒绝没有凭证的请求，
因此没有填写 API Key 的部署根本到不了那一步。它改变的是**默认目的地**——填 Key 之前请先确认上面的接入地址就是
你要发往的地方。内网自建推理服务应当先改地址、协议与模型名，再填凭证。

启用意味着资源、Event、指标、日志和终端输出可能发送到模型端点；在权限和审批允许时，Secret 内容也可能进入当前
任务上下文。平台自身凭证不会发送。

开关还决定 AIOps App 是否出现在桌面：未启用、或接入地址与模型名尚未保存时，Console 不显示该应用图标，
持有 `ai.run` 的用户也看不到入口。Console 通过 `GET /api/v1/ai/tools` 返回的 `enabled` 判断，而不是读取
只有全局管理员可见的平台配置。接入地址或模型名为空时开关不可开启：此时服务端会以
`ai_model_not_configured` 拒绝，Console 直接在开关处说明需要先保存配置。

尚未实现的部分：并发上限与每租户 / 每集群的预算随 AIOps 的编排一起落地，目前页面上没有这两项；API Key 的
静态加密依赖数据库自身的保护，Server 侧不额外加密；接入自建推理服务时，其证书需要由 Server 运行环境本身
信任，平台配置中没有单独的 CA 字段。
