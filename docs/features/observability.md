# 可观测性平台

指标在 Console 中以「监控」应用呈现，按单集群设计：进入后先选择项目，再在工具栏里选定一个目标集群，
其下所有图表都描述这一个集群。日志计划作为独立应用呈现，不并入「监控」。

当前状态：指标链路已完整——集群内三个采集组件、经 Agent 回传、Server 摄取与作用域改写、每集群摄取预算、
集中存储，以及 Console 中一个自定义查询分区与四个图表分区共 119 个具名查询：CPU、内存、磁盘、网络、持久卷与 Kubernetes 对象
状态，覆盖集群 / 节点 / Namespace / 工作负载 / Pod / 容器六个维度的用量、利用率、申请、限制、可分配量、
CPU 限流、饱和度与状态原因，并向下补齐了节点自身的内核、磁盘延迟、套接字与时钟，向上补齐了 kubelet 本身
的健康、Pod 级磁盘与 OOM，以及封锁节点、无法调度 Pod、Job 与持久卷对象状态，并让采集链路观察它自己。
日志、告警与事件仍是规划。

一体镜像、Docker Compose 与 Helm 都自带 VictoriaMetrics 并默认启用指标。未配置指标存储时 Server 不向
Agent 提供摄取能力，集群侧也不部署采集组件，Console 会直接说明本部署未启用指标存储。

数据通路、协议、限额与安全边界见 [Phase 3 可观测性架构设计](../architecture/observability-phase-3.md)。
本文只描述产品侧的能力范围与作用域规则。

## 技术选型

指标与日志由 ZKE 自建链路采集与存储，不依赖 Server 直连集群网络：

- 集群内部署三个组件：vmagent 负责抓取与回传（kubelet 的三个端点各抓一次：资源用量，cAdvisor 的限流、
  Pod 网络与磁盘、容器 OOM，以及卷统计与 kubelet 自身健康），kube-state-metrics 提供节点可分配量与容量、
  Pod 申请与限制、工作负载归属与放置节点、Pod 与节点状态、就绪与调度失败、容器等待与退出原因、
  ResourceQuota、Job 状态、PVC 与持久卷状态，node-exporter 提供磁盘与磁盘延迟、文件系统、网络吞吐与包速率、负载、
  CPU 模式、连接跟踪与 TCP/UDP 计数、套接字、PSI 压力停顿、内核内存与分页、进程与文件描述符、时钟。
  三者由该集群的 Agent **一并安装、一并卸载**，
  Console 中一次操作即可，不需要使用者自己执行 `kubectl apply`；未安装采集的集群行为不变；
- 集群内自己的工作负载通过注解接入：给 Service 或 Endpoints 打上
  `zke-metrics-collector.io/scrape=true` 即可被 vmagent 的 Kubernetes 服务发现抓取，
  scheme、path、port、认证与 TLS 校验用同一组注解描述，不需要重新安装采集组件；
- 采集数据经该集群 ZKE Agent 已有的 QUIC/mTLS 出向连接回传，不新增网络开通要求；
- Server 侧集中存储在 VictoriaMetrics（指标）与后续的 VictoriaLogs（日志）；三个组件各自的镜像、拉取策略与
  资源请求/限制都在「平台配置 → 指标采集」中管理，默认 `victoriametrics/vmagent:v1.149.0`、
  `registry.k8s.io/kube-state-metrics/kube-state-metrics:v2.19.1` 与
  `quay.io/prometheus/node-exporter:v1.12.1`；
- 可视化由 ZKE Console 自建，不集成、不嵌入 Grafana，也不提供 Grafana 数据源。

## 已实现

- 五个分区，按提问的场景分开，而不是按指标分开。「数据探索」紧跟在「采集接入」之后、三个仪表分区之前：
  那三个分区回答的是有人写过面板的问题，它回答其余的那些，而故障期间大多数问题都在"其余"里——把通用的
  工具排在专用的后面，等于让最需要它的时候最不容易找到它。「采集质量」仍然排在最后，因为它解释的是其余
  分区为什么可能是空的：

  | 分区 | 回答什么 |
  | --- | --- |
  | 数据探索 | 预置面板之外的问题：自己书写 MetricsQL 表达式，一次最多五条同时执行 |
  | 集群总览 | 现在有没有出问题：节点就绪、Pod 运行 / 等待 / 失败、工作负载数量五个数字，加集群 CPU 与内存用量、利用率与申请占比、Pod 状态分布、容器重启六条曲线；需要下钻时在同一分区切换 Pod、节点、容器、工作负载、批处理和存储对象视角 |
  | 计算资源 | CPU、内存、节点自身状态与容器状态，按「维度 + 视角」两级选择 |
  | 存储与网络 | 持久卷使用率与 inode、文件系统与 inode 与只读挂载、磁盘吞吐与 IOPS 与繁忙度与延迟队列、网络收发与错误丢包、连接跟踪与 TCP 重传、TCP 连接与套接字内存与 UDP 错误 |
  | 采集质量 | 采集链路自己的状态：各抓取目标的健康度与耗时、每次抓取的样本数与新增序列、节点导出器各 collector 的失败节点数 |

  计算资源的两级选择：

  | 维度 | 视角 |
  | --- | --- |
  | 集群 | 用量与容量、利用率、限制量、CPU 模式 |
  | 节点 | 利用率、用量、饱和度、内存明细、系统、Kubelet、Pod 密度、压力停顿 |
  | Namespace | 用量、申请量、限制量、规模、配额 |
  | 工作负载 | 用量 |
  | Pod | 用量、重启、磁盘、网络 |
  | 容器 | 用量、限流 |

  不把五十张图同时挂在窗口里——每张图都是一次落到共享存储上的查询，一个打开的窗口不应该成为整个部署的
  常驻负载；操作者提问的方式也是一次一个角度；

- **一次看一个集群**：目标集群从当前项目的集群里选，与容器服务、终端选择集群是同一份列表、同一个语义。
  不做「全部集群」也不做多选——把两个集群的曲线加在一起得到的是一个不存在的数，把它们并排画在共享坐标轴上
  则是把两个问题塞进同一张图。集群名在项目内唯一，因此选择器里的名字不需要再加限定就能分辨；
- **对象健康收进集群总览**：Pod、节点、容器、工作负载、批处理与存储对象都在「集群总览」内按具体资源名切换。
  它们回答的是同一个任务——集群现在是否健康以及问题落在哪类对象——不再用含义宽泛且与「容器服务」重叠的
  「Kubernetes 资源」作为侧栏分区。每次仍只加载当前视角，避免把所有对象状态查询同时变成常驻负载；
- **一行筛选器作用于其下所有图**：目标集群、时间范围与自动刷新间隔由分区之间共享。换到另一个分区不必把
  「哪个集群、哪一个小时」再说一遍；
- **时间范围有两种**：跟着时钟走的相对范围（15 分钟到 7 天），和钉住不动的绝对范围。**在任意图表上横向
  拖拽**即可选定一段时间，同一分区内所有图表一起切到这段窗口；工具栏上有一个反向的「扩大范围」。绝对范围
  下自动刷新停摆——一个仍然跟着时钟走的选区会从刚刚指着的东西下面滑走；
- **鼠标停在图上会给出读数**：十字光标按时间对齐，列出该时刻每一条序列的值并按大小排序，同一分区内的图表
  共享光标位置。图例把最新、平均与最大三个数字写在序列名旁边，因此不悬停也能读到，并且可以逐条开关；
- 采样步长由时间范围算出来，只落在固定档位上，始终远低于 Server 的点数上限——点比像素还多的查询是整个
  部署替谁也看不见的东西付钱；
- **利用率有分母**：用量除以该节点（或全部节点）的可分配量。这是 kubelet 单独回答不了的问题——它报告
  用了多少，从不报告有多少；
- **申请量与限制量**：调度器为一个 Namespace 预留、其他工作负载无法使用的部分。申请量远高于实际用量是
  集群里最常见的一种浪费；集群维度把用量、申请量与可分配量画在同一张图上，因为"满了"与"被申请占满了"是
  两种完全不同的处境，只画一条线看不出是哪一种；
- **容量还有第三种会先用完的**：节点的 Pod 容量。CPU 与内存都还有余量的节点，装满 Pod 之后同样调度不进去，
  而这件事在别处只会表现为一句没有数字的"没有可用节点"；
- **CPU 时间花在哪里**：同样是 80% 利用率，花在用户态上和花在内核态、I/O 等待、被抢占上是三种完全不同的
  机器。集群维度按模式堆叠，堆叠的高度就是利用率；节点维度单画被抢占——它来自节点之外，节点内部的利用率、
  负载与压力都解释不了它，而上面的工作负载确实变慢了；
- **节点自己会出的问题**：内核内存（slab、页表、内核栈）不属于任何容器，因此不出现在任何 Pod 的工作集里；
  主缺页与节点 OOM 说明内存压力已经变成了延迟或者杀进程；阻塞进程数说明任务在等存储而不是等 CPU；文件
  描述符用尽会让节点上所有的 accept 与 open 一起失败；节点重启在别处不留痕迹，只有运行时长归零那一刻是
  事件；时钟漂移则一律以别的名义出现——证书未生效、日志乱序、样本因超出摄取窗口被拒；
- **kubelet 本身也是被观测对象**：节点上其余所有数字都是经由它测出来的，因此它出问题时节点看起来反而很
  平静——曲线不是抬升，而是不再变化。运行中的 Pod 与容器数、容器运行时调用的错误率、PLEG 重列的平均时延
  各成一图；PLEG 变大之后，就绪、重启与用量全部迟到，Pod 会因为不属于它们的原因被判为不健康；
- **磁盘延迟与吞吐分开**：吞吐量与 IOPS 说的是设备做了多少，读写延迟与队列长度说的是每次操作花了多久——
  后者才是上面的工作负载真正感受到的东西。繁忙度接近 1 而队列很短的设备是一直在做事，队列涨起来才是排上
  队了。文件系统还有一类空间富余时就已经失败的故障：I/O 错误之后被内核改成只读的挂载点，写入全部失败而
  已用空间纹丝不动；
- **饱和度与利用率分开**：利用率说的是用掉了多少，1 分钟负载、CPU I/O 等待、磁盘繁忙度说的是还跟不跟得上。
  一个 60% 利用率、磁盘繁忙度接近 1 的节点，上面的工作负载都在排队。1、5、15 分钟三档负载与该节点的核数画在
  同一张图上——负载 8 在 64 核节点上是空闲，在 2 核节点上是排队，只有一条线的图回答不了这个问题；1 分钟高而
  15 分钟低是一次尖峰，反过来则是这个节点已经落后了一刻钟；
- **CPU 限流单独成图**：被限流的容器用量恰好等于它被允许的量，在任何用量曲线上都看不出异常，变慢的原因
  只在限流比例这条曲线里。集群维度的限制量与可分配量也画在一起：超卖的集群会在压力下开始限流，具体是哪些
  容器则由容器维度回答；
- **容器维度**：Pod 是一组进程而不是一个，Pod 维度说明这个 Pod 在消耗，容器维度说明是其中哪一个——
  Sidecar 是这个问题最常见的落点。数据来自 kubelet 已经在抓的同一个端点，不新增采集目标；
- **Pod 网络**：节点网卡打满是节点的事实，是谁打满的是紧接着的问题。前者在存储与网络分区，后者在 Pod 维度；
- **持久卷有自己的视角**：PVC 使用率、已用空间与 inode 使用率由挂载它的 kubelet 上报。节点文件系统描述的是
  磁盘，PVC 描述的是声明——一个写满的 PVC 所在的磁盘可能还很空，反过来也一样；
- **网络饱和与网络吞吐分开**：连接跟踪表写满、握手完成却没有进程接收、TCP 重传升高、TIME_WAIT 占满本地
  端口、套接字内存越过内核上限，几种情况下节点的字节计数都完全正常，而请求全部超时。集群 DNS 走 UDP，
  因此 UDP 接收缓冲区溢出单独成图：它在每个 Pod 里都表现为解析超时，却不出现在任何 TCP 计数器上；
- **Pod 维度补齐磁盘、丢包与 OOM**：节点层面能看出某块盘被打满、某张网卡在丢包，看不出是谁。容器 OOM 计数
  与 Kubernetes 的 OOMKilled 也不是一回事——后者只保留最后一次退出原因，Pod 被控制器换掉之后就随之消失；
- **采集链路观察自己**：一屏图表全空的时候，集群闲着、某个抓取目标挂了、某个导出器的 collector 在这些
  节点上跑不起来，是三件事，而集群自身的曲线分不出来。这些序列从第一次安装起就在存储里——采集器为每个目标
  各写七条——此前只有整体健康度被读过。样本数与新增序列同时也是摄取预算花在哪里的答案：前者是每次抓取要
  付的，后者是整个保留期要付的。这个分区放在图表侧而不是「采集接入」里，因为被一屏空图挡住的人要的是
  一条随时间变化的曲线，而「采集接入」回答的是此刻装了什么、在抓什么；
- **压力停顿（PSI）测的是延迟本身**：任务因为拿不到 CPU、内存或磁盘而停下来的时间占比，而不是资源用到了
  多少。需要节点内核提供 `/proc/pressure`（Linux 4.20 及以上），较旧的内核上这个视图没有数据，界面会说明；
- **容器为什么没在跑**：等待原因（CrashLoopBackOff、ImagePullBackOff 等）与退出原因（OOMKilled 等）各成一图。
  重启次数只说明有容器在反复出问题，处理方式却完全不同；OOMKilled 尤其只能在这里看到——内存超限的容器被
  直接杀掉，它在任何用量曲线上都只是突然消失。原因保留 Kubernetes 的英文原值，与 `kubectl describe` 一致，
  并且只采集与查询操作者会处理的那几个取值；
- **Namespace 配额**：ResourceQuota 的已用量占上限的比例。配额用满的 Namespace 会拒绝新建 Pod，而集群本身
  可能还很空闲——这件事在任何用量曲线里都看不见，因为那些工作负载根本没有被创建出来；
- **看起来健康、实际不接活的集群**：被 cordon 的节点不带任何条件、用量一切正常，只是安静地不再接收 Pod；
  调度不上的 Pod 与还在拉镜像的 Pod 同样是 Pending，一个自己会好、另一个在等永远可能不来的容量、容忍或卷；
  就绪探针失败的 Pod 仍然是 Running，却已经被从每个 Service 后面摘掉，而状态分布把这件事画成一片健康；
- **批处理与存储对象**：跑完的 Job 不是缺副本的工作负载，因此副本视角故意不含它——而一个连续失败了一周的
  定时任务在别处看不见，等有人去看的时候它的 Pod 早就不在了。持久卷视角量的是已经挂载的 PVC，卡在 Pending
  的声明恰好落在这个集合之外；Released 与 Failed 的持久卷占着真实的存储，声明已经没了，卷还在；
- **inode 与错误丢包各自成图**：inode 用完的文件系统剩余空间看起来完全正常，写入却全部失败；持续丢包的网卡
  在吞吐曲线上也看不出来；
- **未就绪副本按控制器排序**：3/3 就绪与 1/3 就绪在列表里是同一个绿色对勾，缺得最多的工作负载排在最前；
  期望副本与就绪副本另有一张图，两条线一起看才分得出扩容、副本掉了和滚动更新；
- **分量相加等于总量的图用堆叠面积**：Pod 状态分布、节点就绪状态、容器状态原因——堆叠的高度本身就是一个
  答案（总数变没变），而几条贴地的折线只会互相压着。其余图表一律是折线：把两个节点的利用率叠起来得到的
  是一个不存在的数；
- **该对比的地方画参考线**：利用率与申请占比图上的可分配量、配额使用率图上的配额上限。申请占比越过这条线
  意味着集群已经承诺了超过它拥有的资源，而这正是这张图存在的理由；
- **工作负载维度按控制器汇总**：Deployment 的 Pod 会归到 Deployment 而不是它当前的 ReplicaSet，否则同一个
  工作负载在每次滚动更新后看起来像另一个；
- Pod 与工作负载维度必须给出 Top N：一个集群的 Pod 数量比节点高出几个量级，"全部 Pod"既画不出也没人问，
  把边界写进契约比交给序列上限截断更清楚；
- 采集健康度，同时用作当前有数据的集群清单；
- 「采集接入」按集群列出三个组件各自的状态与镜像、摄取凭证与摄取预算，支持一键安装与卸载；状态来自各集群
  本身，因此手工删除也能被发现。node-exporter 被集群的 Pod Security 策略拒绝时如实显示「已被集群拒绝」
  并说明原因，其余组件照常安装——把它显示成"未安装"会让操作者反复重装；
- 点进某个集群可以看到它当前的采集 Job：内置的 kubelet、kube-state-metrics 与 node-exporter，以及注解
  发现出来的每一个 Service/Endpoints、它们最终生效的 scheme、path、port、认证模式与 TLS 校验方式，还有
  当前就绪的目标地址。这份清单在打开详情时才向该集群索取，列表的状态轮询不为它付出一次全集群
  Service 与 Endpoints 列举；Job 与目标都有上限（500 个 Job、每个 Job 200 个目标），超出时明确标注截断，
  而不是让响应随集群规模增长；
- 节点指标导出器以只读方式挂载宿主机的 `/proc`、`/sys` 与根目录，但**不使用挂载传播**：带上它会让这个组件
  在根挂载为 private 的节点（例如 Docker Desktop 的虚拟机）上直接无法创建容器。代价是该 Pod 启动之后节点上
  新挂的文件系统要等 Pod 重建才会被正确测量；PersistentVolume 与容器运行时分层不受影响，它们本来就不在这个
  导出器上报的范围内；
- 依赖某个组件的视图在数据为空时说明它需要哪个组件，而不是给出一张没有解释的空图；依赖具体条件的视图
  同样如此：PVC、限流与 Pod 网络会说明它们读的是 kubelet 的哪个端点、以及旧的采集安装需要重新安装才会
  抓取它；配额视图说明没有配置 ResourceQuota 的 Namespace 本来就没有数据；压力停顿说明它需要较新的内核。
  抓取配置随安装下发，Server 不会主动改写已经在集群里运行的采集组件；
- 集群总览的两条用量曲线只依赖 kubelet：其余面板都读 kube-state-metrics，而对象导出器异常的集群不应该得到
  一整屏空白——用量数据这时仍在正常上报；
- 每集群的样本速率与活跃序列上限，防止一个集群占满所有集群共用的存储。被拒绝不会静默发生：采集接入列出
  该集群是否被限流、触碰的是哪一项预算、活跃序列的估算值与上限（估算值来自固定大小的概率草图，界面按
  近似值呈现），图表则在受影响集群的曲线下写明空洞由 Server 拒绝造成，而不是采集组件故障；
- 查询响应区分"范围内的集群没有数据"与"该集群正在被限流"：前者可能只是还没装采集组件，后者需要减少集群
  产生的序列。两者的处置完全不同，因此不合并成一句"部分数据不可用"；
- 摄取凭证由 Agent 在集群内生成，从不经过 Server，也不会出现在浏览器里；
- kube-state-metrics 以 `--resources` 与 `--metric-allowlist` 双重收窄，只 `list`/`watch` Node、Pod、
  Namespace、ResourceQuota、PVC、持久卷与五类工作负载对象，**不包含 Secret 与 ConfigMap**，也没有任何写权限。
  安装不需要为 Agent 增加权限：授予它的范围是 Agent 已持有权限的子集，这一点由 Kubernetes 强制；
- 采集配置随安装下发，Server 不会改写已经在集群里运行的采集组件。因此指标族扩充之后，旧安装上的相关面板
  会一直为空，界面在这些面板的空态里写明需要在「采集接入」中重新安装采集，而不是让它读起来像"集群很闲"；
- 权限按集群定域且读写分离：`cluster.metrics.read` 决定能查哪些集群的指标、采集组件状态与当前采集 Job，
  `cluster.metrics.manage` 决定能否安装或卸载采集组件——只能看图表的人可以知道数据从哪来，但无法改变集群里
  运行的东西。「采集接入」因此对只有读取权限的人也可见，只是安装与卸载入口不出现，Server 也照样拒绝；

### 注解接入自己的工作负载

内置的三个采集目标回答的是集群自身的问题。集群里跑的业务有自己的指标端点，它们不该需要一次采集组件重装、
更不该需要把一段抓取配置交给平台去下发。因此接入方式是注解：给 Service 或 Endpoints 打上注解，vmagent 的
Kubernetes 服务发现会在下一个发现周期里把它的**就绪**端点纳入抓取，不重启、不重新安装。

| 注解 | 作用 | 取值 |
| --- | --- | --- |
| `zke-metrics-collector.io/scrape` | 唯一的开关，其余注解只在它为 `true` 时有意义 | `true` |
| `zke-metrics-collector.io/scheme` | 抓取协议 | 留空（默认 `http`）、`http`、`https` |
| `zke-metrics-collector.io/path` | 指标路径 | 留空（默认 `/metrics`）或以 `/` 开头的路径 |
| `zke-metrics-collector.io/port` | 覆盖端口，留空时使用 Endpoints 自身的端口 | 1–65535 |
| `zke-metrics-collector.io/auth` | 认证模式 | 留空或 `none`；`service-account` 表示携带采集组件自己的 ServiceAccount Token |
| `zke-metrics-collector.io/tls-insecure-skip-verify` | 是否跳过服务端证书校验 | 留空或 `false`；`true` 仅在 `https` 下有效 |

同名 Service 与 Endpoints 上的同一个注解以 **Endpoints 为准**：它是更具体的那个对象，也是外部后端唯一能
打注解的地方；Endpoints 没写的注解沿用 Service 的值。开关本身也遵循这个规则，因此没有 Service 的
Endpoints 可以独立接入。

这里刻意受限，因为注解是集群内任何能改 Service 的人都能写的输入：

- **注解不是抓取配置**。它只能在上面这张表的词汇里取值，不能注入 relabel 规则、不能改抓取间隔、
  不能指定 Server 侧的目标标签。ZKE 自己使用的 `zke_*` 与临时标签在每个 Job 的最后一律丢弃；
- **认证只有两种模式，且都不读取集群凭证**。`service-account` 携带的是采集组件自己那份投射 Token，
  并且**只允许在 `https` 下使用**——用明文发送 Bearer Token 等于把它交给链路上的任何人。注解不支持引用
  Secret：那会把一个指标注解变成集群凭证读取器，采集组件的 ClusterRole 里也因此没有 Secret 与 ConfigMap；
- **看不懂的值直接丢弃目标，而不是回退到默认值**。把 `path` 写成 `metrics` 时不会去抓 `/metrics`，
  把 `port` 写成 `70000` 时不会去抓一个不存在的端口：抓取配置与「采集接入」详情页读的是同一套取值规则，
  一个界面上说着在采集、实际却在抓别的东西的集群，比两者都没有更难排查；
- **只抓就绪端点**，未就绪地址不会被抓取，也不会出现在详情页的目标列表里。

采集组件为此需要的额外权限是 Service、Endpoints 与 Pod 的 `get`/`list`/`watch`——服务发现要读的元数据，
仅此而已，没有任何写权限。

Console 两处都指向这套注解：「采集接入」的帮助入口列出完整词汇与约束，
[容器服务](container-service.md)的服务与路由在编辑 Service 或 Endpoint 时可以一键填入。
AIOps 随 Server 发布了「接入自定义指标采集」技能，写明这套注解词汇、写错时的表现，以及接入之后用哪条查询
验证目标是否真的被抓到；见 [AIOps 智能运维](ai-assistant.md#技能)。

### 数据探索

故障通常不是任何一张预置面板回答的问题。「数据探索」是写下那个问题的地方：

- **自己书写表达式**。查询语言是 VictoriaMetrics 的 MetricsQL（PromQL 的超集），界面上有一个链接直接指向
  [MetricsQL 语法文档](https://docs.victoriametrics.com/victoriametrics/metricsql/)——指向 Prometheus 的
  文档会描述一门比输入框实际接受的更小的语言；
- **多条表达式画在同一张图上**，一次最多五条。每一条可以单独**隐藏**（保留文本但不执行）、单独看到自己的
  耗时，失败也只影响自己——第二行的笔误不会让第一行的图变空。隐藏、恢复与删除都会立即重新执行：一条已经
  隐藏的表达式，它的曲线还留在图上，就是图和上面的编辑器在互相矛盾。连续操作会合并成一次请求；
- **结果三种读法**：图表（曲线，共享十字光标与横向拖拽选区）、表格（按表达式分组，标签成为列，区间查询
  附最小 / 中位 / 最大 / 最新，瞬时查询只有一列「值」）、JSON（原样的响应，包含实际执行的表达式，按
  与 YAML 编辑器同一套 `--code-*` 变量着色，可一键复制）；
- **区间与瞬时**两种查询。切换即重新执行，不需要再点一次「执行查询」——它换的是问题本身，而不是对问题的
  编辑；瞬时结果每条序列只有一个采样点，没有曲线可画，「图表」页签会置灰并说明原因，界面直接落到表格。
  改写表达式**文本**则不会自动执行：那会在每一次按键上触发一次查询，由「执行查询」按钮和「表达式已修改」
  提示覆盖；
- **数值按原样显示**，不做单位换算。自定义表达式没有声明单位，`node_memory_working_set_bytes` 与
  `kube_pod_container_status_restarts_total` 走的是同一条路径，从指标名去猜单位只会在最要紧的地方猜错。
  所以图例、表格与光标读数给的是分组后的原值（`2,061,271,040`），坐标轴因为只有四五个字符的宽度而使用
  与单位无关的 SI 前缀（`2G`）——而且只向上取，`0.5` 就是 `0.5`，不会写成 `500m`；
- 目标集群、时间范围与自动刷新与其他分区共用同一行筛选器：换范围、点刷新或自动刷新到点，探索的结果跟着
  重算，而不是留在一个已经没人在问的窗口上；
- 「保存的查询」与语法文档入口在应用工具栏上——它们属于这个界面而不是属于某一条表达式；
- 一个「清空」把表达式与结果一起归零，回到刚打开的样子；
- 表达式在离开分区之后仍然保留——切到「计算资源」看一眼再回来，写了一半的表达式还在。

**表达式决定读哪些序列，永远不能决定读哪个集群。** 提交之后，Server 用 VictoriaMetrics 自己的解析器解析
表达式，把其中**每一个**序列选择器都改写为携带 `zke_cluster_id="<当前目标集群>"`，并且**删除**作者自己写在
表达式里的同名条件——是替换而不是求交，所以把别人 runbook 里的表达式连同过滤条件一起粘过来，得到的是自己
集群的答案，而不是一张需要解释十分钟的空图。改写后的表达式原样返回并显示在 JSON 视图里：这是 Server 唯一
一处重写用户查询的地方，看不到的改写就是无法核对的改写。

作用域不依赖这一次改写做对：重写后的表达式会被重新解析校验，任何一个选择器没有携带该条件都会被拒绝执行；
同一条件还会作为 `extra_label` 交给存储，由存储对它自己解析出的每一个选择器再施加一次。

成本与具名查询用同一套边界（时间范围、步长、点数与序列上限），另外限制单次请求的表达式条数、单条表达式的
长度，以及同一个人和整个 Server 的在途请求数——超出时明确返回「并发的自定义查询过多，请稍后重试」，而不是
排队。

### 保存的查询

写对一条表达式是这件事里最贵的部分，它下周还会被用到——被写它的人，也被之后值班的人。所以表达式可以命名
保存，按项目归属：

- **两种可见范围**：`仅自己可见` 与 `项目内共享`。共享的条目会标出是谁分享的；
- 从选择器里点一条即可填进当前正在写的那一行；那一行已经有内容时会新开一行，而不是覆盖没有保存过的工作；
- 条目可以改名、改说明、改可见范围与改表达式，也可以删除；没有权限的条目上，入口是禁用并写明原因的，而不是
  消失的；
- 条目多起来之后选择器会出现筛选框；每个项目最多保存 200 条。

**共享一条表达式不会共享任何集群的数据**：条目只存名称、说明与表达式文本，不存集群，也不携带任何权限。
运行时读哪个集群由运行的人当时选定的目标决定，再由上面的改写写进每一个选择器——所以一个人写下、另一个人
运行的表达式，描述的始终是运行者本来就可以读的集群。

权限因此是策展而不是访问：看列表、保存自己的私有条目只需要 `cluster.metrics.read`；把条目共享进项目、以及
修改或删除已经共享的条目需要 `cluster.metrics.manage`。私有条目只有作者本人可写。作者账号被删除时，共享的
条目留在项目里（署名变为空），私有条目随之删除。保存类写入会写审计，记录名称与可见范围，不记录表达式正文。

## 规划能力

- 日志查询与 Kubernetes Event；
- 告警规则与告警记录；
- 多集群资源对比。

上述能力按切片推进，顺序与范围见 [Roadmap](../roadmap.md)。

分区里提供的是围绕上述场景设计的固定视图，不是通用仪表盘编辑器：布局与面板的持久化是另一件产品。需要一张
预置面板之外的图时，路径是「数据探索」——写一条表达式、当场看结果，并按需把**表达式**（而不是布局）保存
下来。

## 作用域与数据身份

`cluster_id` 是指标与日志唯一不可变的数据身份，由 Server 在摄取时按 Agent 的 mTLS 连接身份强制写入：
摄取网关先删除批次中所有 `zke_` 前缀的标签，再写入自己的 `zke_cluster_id`，因此集群侧无论上报什么都
无法冒充另一个集群。

Tenant 与 Project 不写入存储：Cluster 的归属是 Server 数据库中的可变关系，写进时间序列标签会让同一集群的
历史数据按旧归属分裂。查询时由 Server 把调用者的可见范围展开成一组 `cluster_id`，再作为强制过滤注入查询。
`cluster_name` 只能作为展示属性，不能替代 `cluster_id` 作为数据身份。

每次查询必须指定一个目标集群，Server 校验调用者在 `cluster.metrics.read` 上确实可以读取它，再把它作为
强制过滤注入查询——具名查询注入模板，自定义表达式注入解析后的每一个序列选择器。目标集群不可读时返回 403，且不区分「不存在」与「不属于你」——区分它们会让这个接口
变成探测范围外集群 ID 的手段。读取权限词为 `cluster.metrics.read`，采集组件状态与采集 Job 详情也用它；采集启停为
`cluster.metrics.manage`。

Console 侧的「监控」应用与其他应用一样需要先选择项目才会打开，目标集群从该项目的集群里选：「采集接入」
按项目列出集群，图表按选定的那一个集群绘制，没有作用域时没有可操作的对象。

## 不做的事

- 不向浏览器开放存储后端的原始查询接口。自定义表达式只经 Server 的查询接口，由 Server 解析、把目标集群
  强制改写进每一个选择器，并施加与具名查询相同的成本上限；
- 不集成 Grafana：它的权限体系与 ZKE 的 Tenant/Project/RBAC 无法对齐，嵌入还会带来第二套导航、主题与
  登录；需要 Grafana 的使用者可以自行连接自己的 VictoriaMetrics，ZKE 不为此提供数据源或代理；
- 不做通用仪表盘编辑器（自定义的是表达式，不是布局）；
- 不托管或迁移用户已有的 Prometheus 生态；
- 可观测性是可降级能力，存储不可用时不影响集群接入、容器服务与终端。
