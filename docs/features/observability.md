# 可观测性平台

可观测性平台是多集群应用，用户进入时无需先选择集群。

当前状态：指标链路已完整——集群内三个采集组件、经 Agent 回传、Server 摄取与作用域改写、每集群摄取预算、
集中存储，以及 Console 中四个图表分区共 50 个具名查询：CPU、内存、磁盘、网络与 Kubernetes 对象状态，覆盖
集群 / 节点 / Namespace / 工作负载 / Pod 五个维度的用量、利用率、申请、限制与可分配量。日志、告警、事件与
集群标签体系仍是规划。

一体镜像、Docker Compose 与 Helm 都自带 VictoriaMetrics 并默认启用指标。未配置指标存储时 Server 不向
Agent 提供摄取能力，集群侧也不部署采集组件，Console 会直接说明本部署未启用指标存储。

数据通路、协议、限额与安全边界见 [Phase 3 可观测性架构设计](../architecture/observability-phase-3.md)。
本文只描述产品侧的能力范围与作用域规则。

## 技术选型

指标与日志由 ZKE 自建链路采集与存储，不依赖 Server 直连集群网络：

- 集群内部署三个组件：vmagent 负责抓取与回传，kube-state-metrics 提供节点可分配量与容量、Pod 申请与限制、
  工作负载归属与放置节点、Pod 与节点状态，node-exporter 提供磁盘、文件系统、网络、负载与 CPU 模式。三者由该集群的 Agent **一并安装、一并卸载**，
  Console 中一次操作即可，不需要使用者自己执行 `kubectl apply`；未安装采集的集群行为不变；
- 采集数据经该集群 ZKE Agent 已有的 QUIC/mTLS 出向连接回传，不新增网络开通要求；
- Server 侧集中存储在 VictoriaMetrics（指标）与后续的 VictoriaLogs（日志）；三个组件各自的镜像、拉取策略与
  资源请求/限制都在「平台配置 → 指标采集」中管理，默认 `victoriametrics/vmagent:v1.149.0`、
  `registry.k8s.io/kube-state-metrics/kube-state-metrics:v2.19.1` 与
  `quay.io/prometheus/node-exporter:v1.12.1`；
- 可视化由 ZKE Console 自建，不集成、不嵌入 Grafana，也不提供 Grafana 数据源。

## 已实现

- 四个分区，按提问的场景分开，而不是按指标分开：

  | 分区 | 回答什么 |
  | --- | --- |
  | 总览 | 现在有没有出问题：集群、节点就绪、Pod 运行 / 等待 / 失败、工作负载数量六个数字，加 CPU 与内存利用率、Pod 状态分布、容器重启四条曲线 |
  | 计算资源 | CPU 与内存，按「维度 + 视角」两级选择 |
  | 存储与网络 | 文件系统与 inode、磁盘吞吐与 IOPS 与繁忙度、网络收发与错误丢包 |
  | Kubernetes 资源 | Pod 状态与容器重启、节点就绪与压力、工作负载未就绪副本 |

  计算资源的两级选择：

  | 维度 | 视角 |
  | --- | --- |
  | 集群 | 用量与容量、利用率、限制量 |
  | 节点 | 利用率、用量、饱和度、Pod 密度 |
  | Namespace | 用量、申请量、限制量、规模 |
  | 工作负载 | 用量 |
  | Pod | 用量、重启 |

  不把五十张图同时挂在窗口里——每张图都是一次落到共享存储上的查询，一个打开的窗口不应该成为整个部署的
  常驻负载；操作者提问的方式也是一次一个角度；
- **一行筛选器作用于其下所有图**：集群范围、时间范围与自动刷新间隔由分区之间共享。换到另一个分区不必把
  「哪些集群、哪一个小时」再说一遍；
- **时间范围有两种**：跟着时钟走的相对范围（15 分钟到 7 天），和钉住不动的绝对范围。**在任意图表上横向
  拖拽**即可选定一段时间，同一分区内所有图表一起切到这段窗口；工具栏上有一个反向的「扩大范围」。绝对范围
  下自动刷新停摆——一个仍然跟着时钟走的选区会从刚刚指着的东西下面滑走；
- **鼠标停在图上会给出读数**：十字光标按时间对齐，列出该时刻每一条序列的值并按大小排序，同一分区内的图表
  共享光标位置。图例把最新、平均与最大三个数字写在序列名旁边，因此不悬停也能读到，并且可以逐条开关；
- 采样步长由时间范围算出来，只落在固定档位上，始终远低于 Server 的点数上限——点比像素还多的查询是整个
  部署替谁也看不见的东西付钱；
- **利用率有分母**：用量除以该节点（或全部节点）的可分配量。这是 kubelet 单独回答不了的问题——它报告
  用了多少，从不报告有多少；
- **申请量与限制量**：调度器为一个 Namespace 预留、其他工作负载无法使用的部分。申请量远高于实际用量是
  集群里最常见的一种浪费；集群维度把用量、申请量与可分配量画在同一张图上，因为"满了"与"被申请占满了"是
  两种完全不同的处境，只画一条线看不出是哪一种；
- **容量还有第三种会先用完的**：节点的 Pod 容量。CPU 与内存都还有余量的节点，装满 Pod 之后同样调度不进去，
  而这件事在别处只会表现为一句没有数字的"没有可用节点"；
- **饱和度与利用率分开**：利用率说的是用掉了多少，1 分钟负载、CPU I/O 等待、磁盘繁忙度说的是还跟不跟得上。
  一个 60% 利用率、磁盘繁忙度接近 1 的节点，上面的工作负载都在排队；
- **inode 与错误丢包各自成图**：inode 用完的文件系统剩余空间看起来完全正常，写入却全部失败；持续丢包的网卡
  在吞吐曲线上也看不出来；
- **未就绪副本按控制器排序**：3/3 就绪与 1/3 就绪在列表里是同一个绿色对勾，缺得最多的工作负载排在最前；
- **工作负载维度按控制器汇总**：Deployment 的 Pod 会归到 Deployment 而不是它当前的 ReplicaSet，否则同一个
  工作负载在每次滚动更新后看起来像另一个；
- Pod 与工作负载维度必须给出 Top N：一个集群的 Pod 数量比节点高出几个量级，"全部 Pod"既画不出也没人问，
  把边界写进契约比交给序列上限截断更清楚；
- 采集健康度，同时用作当前有数据的集群清单；
- 「采集接入」按集群列出三个组件各自的状态与镜像、摄取凭证与摄取预算，支持一键安装与卸载；状态来自各集群
  本身，因此手工删除也能被发现。node-exporter 被集群的 Pod Security 策略拒绝时如实显示「已被集群拒绝」
  并说明原因，其余组件照常安装——把它显示成"未安装"会让操作者反复重装；
- 依赖某个组件的视图在数据为空时说明它需要哪个组件，而不是给出一张没有解释的空图；
- 每集群的样本速率与活跃序列上限，防止一个集群占满所有集群共用的存储。被拒绝不会静默发生：采集接入列出
  该集群是否被限流、触碰的是哪一项预算、活跃序列的估算值与上限（估算值来自固定大小的概率草图，界面按
  近似值呈现），图表则在受影响集群的曲线下写明空洞由 Server 拒绝造成，而不是采集组件故障；
- 查询响应区分"范围内的集群没有数据"与"该集群正在被限流"：前者可能只是还没装采集组件，后者需要减少集群
  产生的序列。两者的处置完全不同，因此不合并成一句"部分数据不可用"；
- 摄取凭证由 Agent 在集群内生成，从不经过 Server，也不会出现在浏览器里；
- kube-state-metrics 以 `--resources` 与 `--metric-allowlist` 双重收窄，只 `list`/`watch` Node、Pod、
  Namespace 与五类工作负载对象，**不包含 Secret 与 ConfigMap**，也没有任何写权限。安装不需要为 Agent 增加
  权限：授予它的范围是 Agent 已持有权限的子集，这一点由 Kubernetes 强制；
- 权限按集群定域且读写分离：`cluster.metrics.read` 决定能查哪些集群的指标，`cluster.metrics.manage`
  决定能否安装或卸载采集组件——只能看图表的人无法改变集群里运行的东西。

## 规划能力

- 日志查询与 Kubernetes Event；
- 告警规则与告警记录；
- 多集群资源对比；
- 集群标签体系。

上述能力按切片推进，顺序与范围见 [Roadmap](../roadmap.md)。

界面提供的是围绕上述场景设计的固定视图，不是通用仪表盘编辑器：自定义面板需要自由查询表达式，与"只开放
具名查询"的安全边界冲突。

## 作用域与数据身份

`cluster_id` 是指标与日志唯一不可变的数据身份，由 Server 在摄取时按 Agent 的 mTLS 连接身份强制写入：
摄取网关先删除批次中所有 `zke_` 前缀的标签，再写入自己的 `zke_cluster_id`，因此集群侧无论上报什么都
无法冒充另一个集群。

Tenant 与 Project 不写入存储：Cluster 的归属是 Server 数据库中的可变关系，写进时间序列标签会让同一集群的
历史数据按旧归属分裂。查询时由 Server 把调用者的可见范围展开成一组 `cluster_id`，再作为强制过滤注入查询。
`cluster_name` 只能作为展示属性，不能替代 `cluster_id` 作为数据身份。

可观测性平台默认提供用户权限范围内的全局视图，同时允许按集群和 Namespace 缩小范围。全局视图不代表全局
操作权限：查询结果始终受 Tenant、Project 与 RBAC 边界约束，读取权限词为 `cluster.metrics.read`，
采集启停为 `cluster.metrics.manage`。

Console 侧的可观测性应用与其他应用一样需要先选择项目才会打开：「采集接入」按项目列出集群，没有作用域时
没有可操作的对象。指标查询本身仍按调用者在 `cluster.metrics.read` 上的完整可见范围执行，不因当前选择的
项目而收窄。

## 不做的事

- 不向浏览器开放自由 PromQL 或存储后端的原始查询接口，Console 只能调用 Server 定义的具名查询；
- 不集成 Grafana：它的权限体系与 ZKE 的 Tenant/Project/RBAC 无法对齐，嵌入还会带来第二套导航、主题与
  登录；需要 Grafana 的使用者可以自行连接自己的 VictoriaMetrics，ZKE 不为此提供数据源或代理；
- 不做通用仪表盘编辑器；
- 不托管或迁移用户已有的 Prometheus 生态；
- 可观测性是可降级能力，存储不可用时不影响集群接入、容器服务与终端。
