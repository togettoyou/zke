# Helm 应用

「Helm 应用」是 Console 桌面上的独立应用，负责一件容器服务不做的事：**改变**集群里装了什么。

容器服务里的「Helm 应用」区块回答「这个命名空间里装了哪些应用、什么 Chart 版本、用的什么 values」，读的是
Helm 自己的存储。本应用是另一半：选 Chart、编辑 values、预览渲染结果、安装、升级、回滚、卸载。两者共用同一份
Release 数据，入口不同是因为它们要的工作面不同——改一个 Release 需要一个可编辑、可比对、可反悔的页面，而不是
资源列表里的一个抽屉。

- 渲染与写入由**目标集群的 Agent** 用 Helm 自己的引擎完成，Server 不渲染 Chart，也不代写 Release Secret。
- 可安装的 Chart 只来自平台管理员维护的仓库目录。应用中没有任何接受任意地址的入口。
- 仓库可以要求 Chart 带有**可校验的来源证明**：不通过校验的归档不会被安装，也不会被浏览。
- Chart 自带的 `values.schema.json` 在请求离开 Server 之前就会生效，不合法的 values 不会送进集群。
- 安装与升级**必须先预览**：`dry_run` 用完全相同的请求在目标集群渲染一次，给出将要应用的清单，不写入任何对象。
- 四种变更都不是一次 HTTP 请求内完成的：请求启动一个**操作**并立刻返回它的身份，进度、日志与结果从操作账目
  读取。这也是为什么一次等待就绪的安装能在界面上看见集群正在等什么。

## 为什么由 Agent 执行

Release 不是 Kubernetes 的一种资源。Helm 3 把每次修订存成一个 `helm.sh/release.v1` 类型的 Secret，Chart、
values、渲染出的清单与 NOTES 都在里面；Chart 创建出来的 Deployment、Service 与 PVC 是普通对象，不带任何指回
Release 的引用。

要正确地安装或升级一个 Release，必须跑 Helm 自己的那一套：模板引擎、值合并、Hook 与执行顺序、历史改写。由
Server 拼一个「差不多」的实现去写 Release Secret，会破坏真正的 `helm` 客户端依赖的历史——而一个只写对了一半的
Release 比没有这个功能更难收拾。

所以分工是：

| 位置        | 做什么                                                                       |
| ----------- | ---------------------------------------------------------------------------- |
| Console     | 选 Chart、编辑 values、选开关、审阅预览                                      |
| Server      | 鉴权、审计、从仓库目录取 Chart 包、把请求与 Chart 交给目标集群的 Agent       |
| Agent       | 用 Helm 引擎渲染并写入，检查渲染结果是否越界，把 Helm 的结论原样报告回来      |

Server 与 Agent 之间为此新增了一条业务 Stream（`STREAM_KIND_HELM`，能力标识 `helm.v1`）。Chart 包与 values
文档跟在请求消息之后按字节流传输——Chart 远大于一个协议帧。Agent 不从自己的文件系统读任何东西：没有 Helm home、
没有仓库缓存、没有插件目录，因此 Chart 不会被节点上碰巧存在的同名文件替换掉。

不支持 Helm 的 Agent 会被直接拒绝（`424 helm_unsupported`），不会退回到某种「Server 自己写 Secret」的降级路径。

Agent 还可以声明 `helm-progress.v1`。声明了的，在操作进行当中把 Helm 自己的日志逐条送回 Server；没有声明的，
操作照常执行，少的是执行期间的说明而不是执行本身。

## 一次变更是一个操作，不是一次请求

安装、升级、回滚、卸载都不在一次 HTTP 请求里完成。它们下载 Chart、渲染、写入应用拥有的每一个对象，并且默认
还要等这些对象就绪——正常情况下就是几分钟。

按一次请求来做有两个后果，而且都不是理论上的：请求熬过了 Server 的操作超时并以失败返回，集群却继续把 Release
装完了，于是一次成功的安装被报告成错误，之后的重试又撞上那个已经存在的 Release；而在它敞着的整段时间里，界面
上没有任何可读的东西，慢的下载和永远不会应答的集群长得一模一样。

所以：

1. 写入接口返回 `202` 和一个**操作身份**，不返回 Release——那一刻还没有 Release。
2. 操作在 Server 上被记账：它走到了哪个阶段、Server 与集群分别报告了什么、最后的报告或失败原因。
3. Console 在操作进行期间反复读取这份账目（`GET .../helm-operations/{operation_id}`），结束后停止。
4. 真正约束这次操作的期限是 Helm 自己的等待上限与 Agent Stream 的超时，而不是某个 HTTP 请求的期限。

账目分三个阶段，是被上报的而不是猜出来的——流水线的耗时无法从输入推断：

| 阶段                | 内容                                                                 |
| ------------------- | -------------------------------------------------------------------- |
| `resolving_chart`   | 读取仓库索引、确定版本、取回归档、按仓库的签名策略校验来源           |
| `validating_values` | 按 Chart 自带的 `values.schema.json` 校验                            |
| `executing`         | 集群渲染并写入；这里的每一行是 Helm 自己的日志原文，由 Agent 转发    |

`executing` 阶段的日志是这次改动的重点：`beginning wait for 6 resources with timeout of 5m0s` 这样一行，
把「四分钟什么都没有」变成「四分钟里在等一件说好要等的事」。日志有上限，超出时丢弃中间的一段并明确标注——
开头说明这次操作要做什么，结尾说明它做成了没有，中间上千条相同的轮询没人会读。

账目**只保存在 Server 进程内**，结束后保留一段时间（30 分钟）再丢弃，且只有启动它的那个操作者能读到它。
它的价值只等于它所描述的那次操作：操作结束并被读过之后，真正留下来的是 Release 本身、它的修订历史与审计记录，
这三样都存得好好的。Server 重启会丢失账目，但不会丢失操作——执行它的是 Agent，Release 该装还是装了。

限制成「启动它的那个人」是有原因的：账目里的报告带着渲染出的清单，其中可能包含 Chart 生成的 Secret。这意味着
读这份账目不会泄露任何它在启动时没有返回过的东西，也正因如此，这两个读接口不写审计——每秒一条的轮询记录会把
真正说明「谁改了这个 Release」的那一条埋掉。变更本身由写入接口在操作结束时记一次，记的是它的结果。

## Chart 仓库目录

Chart 必须有来源，而 ZKE 不接受调用方临时指定的来源：能装什么由持有 `helm.repository.manage` 的平台管理员决定。
目录是平台级的——Chart 是软件来源，不是某个 Project 的基础设施；而「能否把它装进某个集群」由集群权限决定，
与它来自哪个仓库无关。

一条目录条目包含：名称、说明、仓库地址、可选的用户名与口令、可选的自定义 CA、是否跳过 TLS 校验、是否启用，
以及这个仓库对 Chart 签名的要求（见下一节）。

- **地址**必须是绝对的 http 或 https 地址，且不得内嵌凭证。Server 在存储时校验一次，在真正发起请求前再校验
  一次——URL 是这台 Server 会去访问的地方，所以在使用点上也要判定，而不是只在录入点。
- **口令只写不读**。任何接口都不返回它，读取方只会看到 `has_credentials` 说明是否配置过。更新时不传该字段表示
  保留，传空字符串表示清除。凭证以请求头发送，不会出现在 URL、日志或错误文案里。
- **自定义 CA 原样返回**。它是公开证书而不是机密：读不回它的编辑表单也保不住它——改个名字保存一下，提交的
  就是一个空字段，配置好的 CA 会跟着消失。口令没有这个问题，因为它是三态的。
- **跳过 TLS 校验**是一次明确且可审计的选择，会显示在列表里，而不是某种静默回退。
- **停用**不影响已安装的 Release：Release 自带安装时使用的 Chart。删除仓库同理。

搜索在 Server 端完成：公开仓库的索引动辄数千个 Chart，把它们全下发到浏览器里过滤，正是缓存要避免的下载。

Server 向仓库发起的请求有明确边界：整个交换有超时上限，索引与 Chart 包各有大小上限，https 的重定向不会被跟进
到 http（否则凭证会经明文一跳）。

### 发布在 OCI 镜像仓库里的 Chart

Helm 3.8 之后 Chart 可以推送到镜像仓库而不是静态归档服务器，一个普通的 HTTP 仓库也可能指向那里：它继续发布
列出全部 Chart 与版本的 `index.yaml`，只是那些版本的 `urls` 是 `oci://` 引用。**索引仍然回答「有什么、有哪些
版本」，所以搜索、列表和版本历史全都照旧，变的只有下载这一步。**

ZKE 直接按 OCI distribution 协议拉取，而不是调用 Helm 自己的 registry 客户端：后者会读 `~/.docker/config.json`
与 Helm 的凭证文件，那会让这台 Server 能拉到什么取决于谁在这台机器上登录过，也会把那些凭证发给索引恰好指到的
任何主机。这里**不读任何环境里的凭证**。

- **认证只发给管理员填写的那个主机。** 镜像仓库的主机名来自索引，而索引是这个仓库自己提供的文档；把存下来的
  口令发给它随便写的主机，等于把「这个仓库需要口令」变成一种收集口令的办法。同一台主机同时提供索引和镜像仓库
  的私有部署——Harbor、Artifactory 就是这样——不受影响。
- **TLS 沿用该仓库的设置**：自定义 CA 与「跳过校验」都是管理员为这个仓库做出的选择，它指向的镜像仓库按同样的
  条件访问。
- **按媒体类型认 Chart**，不按层的位置：manifest 里还有 config，可能还有 provenance 文件，取「第一层」迟早会
  把其中之一交给 Chart 解析器。多平台 index 会被指名拒绝——Chart 不按平台构建。
- **摘要校验**：拉到的字节按 manifest 给出的 digest 与 size 校验。这份归档接下来就要交给 Agent 应用到集群，
  digest 是镜像仓库对「发布出去的是什么」的原话。
- **大小上限在下载之前判定**：manifest 已经写明了层的大小，超过上限的归档不必先下载再拒绝。
- 镜像仓库上不存在的 tag 报为「Chart 不存在」（404），与「索引里没有这个版本」是同一个答案；让操作者回去检查
  一个工作正常的镜像仓库只会浪费时间。
- 整个拉取（令牌、manifest、blob）共用一个超时上限，与 HTTP 路径一致。

## Chart 来源证明

索引里的 `digest` 只说明**仓库正在提供它自己发布的内容**，它不说明这份归档是谁生产的。仓库是一台 Web 服务器：
能往上写的人就能发布 Chart，挡在它前面的镜像或代理也能在传输中把归档换掉。而这份归档接下来会被渲染进集群。

Helm 对这件事的答案是发布在归档旁边的分离签名：`<chart>-<version>.tgz.prov` 是一份 PGP 明文签名文档，正文是
Chart 的元数据和一张文件摘要表。校验它同时证明了两件事——**平台信任的某把密钥签署了这张表**，且**手上的归档
正是表中写的那一份**。

信任的决定属于仓库条目，因为决定就是在那里做的：一个仓库是一个发布方，它用哪些密钥签名是它的属性而不是平台的。
所以策略按仓库设置：

| 策略                | 含义                                                                     |
| ------------------- | ------------------------------------------------------------------------ |
| `disabled`          | 不获取也不校验来源证明。公开仓库通常不签名，这是默认值。                 |
| `verify_if_present` | 仓库发布了 `.prov` 就校验，没有发布则放行。                              |
| `required`          | 拒绝一切无法归因到该仓库密钥的归档。                                     |

`verify_if_present` 是**过渡状态而不是安全边界**：能替换归档的一方也能删掉它旁边的文件。它的用处是发布方正在
推进签名、部分版本还没有签名的那段时间。要注意的是，这个策略只放行**没有签名**的情况；带着一份校验不通过的
签名的 Chart 不属于这种情况，两个策略都会拒绝它——那不是「没签名」，那是「不是它自称的那个东西」。

- **策略与密钥是一对，一起校验。** 没有密钥的策略在 `required` 下会拒绝一切 Chart，在 `verify_if_present` 下会
  放行一切 Chart，而界面上仍然显示着「在校验」。因此除 `disabled` 外，必须至少配置一把公钥；这条约束同时写在
  Server 和数据库上。反过来，先录入密钥、之后再切换策略是允许的。
- **密钥是公钥，因此可读回。** 与口令不同，密钥环原文会被原样返回——在三把密钥中增删一把必须能编辑现有内容。
  接口同时返回解析后的**指纹与身份**：指纹是 PGP 密钥中唯一能标识自身的部分，而用户 ID 是密钥所有者自己写的
  自由文本。
- **摘要表按文件名绑定摘要，所以文件名也是被证明的一部分。** 校验时接受两个名字：`helm package` 产生的
  `<chart>-<version>.tgz`，以及索引给出的下载 URL 的文件名（URL 是仓库自己选的）。只按摘要匹配会丢掉这条绑定的
  另一半，因此不这么做。
- **`.prov` 从哪里取**：HTTP 路径上是归档 URL 加 `.prov`，仓库没有发布时回 404——那是一个答案而不是一次失败，
  它是否可接受由策略决定。OCI 路径上它是同一个 manifest 里按媒体类型认出的一层，所以「有没有」是免费的，只有
  真正取回它才是第二次请求，而在没有人会校验时这一步会被跳过。
- **校验发生在取 Chart 的那一步**，因此浏览与安装走的是同一道门：策略生效时，一个校验不通过的归档连模板都读不到。
  把它的模板照常显示出来，等于把一份来路不明的文档呈现得像是仓库的。
- **每一次都校验，包括缓存命中。** 校验是一次哈希加一次几 KB 上的 PGP 运算；把**结论**缓存下来，意味着一把已经
  被撤下的密钥仍然在为磁盘上的旧归档背书。仓库条目一经修改，它的整个缓存目录本来就会被删除（见下文），所以盘上
  的归档总是在当前策略下取回的；`.prov` 与归档作为一对存放，sidecar 另外记下「当时是否问过来源证明」，避免把
  「仓库没有发布」和「那时还没有人会问」当成同一件事。

签名校验失败与「仓库读不到」是不同的答案：仓库回答了，Chart 也在，失败的是平台自己对它的要求，因此返回 422
（`chart_unsigned` / `chart_signature_invalid`）而不是 502。这两种拒绝都发生在集群被联系之前，什么都没有写入，
调用方的 `Idempotency-Key` 仍然可以在修好之后原样重试。

## values.schema.json

Chart 可以打包一份 `values.schema.json`，那是 Chart 作者对「什么是合法配置」的声明：哪些键必填、各自是什么
类型、允许哪些取值。Helm 在渲染时会应用它——在 Agent 上，在一条 Stream 的另一端，在 Server 已经取过 Chart、
幂等键已经发出去之后。

Server 在请求离开之前再应用一次同一份规则（用的就是 Helm 自己的 `CoalesceValues` 与 `ValidateAgainstSchema`）。
它买到的不是第二种意见，而是失败发生的**位置**：

- 操作者在集群被联系之前就看到是哪个键不对，而不是等一次往返回来一段渲染错误；
- 不占用幂等键——这类拒绝可以证明什么都没写，正是 Agent 的重放缓存同样不予占用的那一类；
- 目标集群不必为一份注定渲染不出来的 Chart 跑一次 Helm。

**Agent 上的 Helm 仍然是权威。** 这里不会放行 Helm 会拒绝的东西，而在看不到同一份文档时它也不猜：升级时若选择
「沿用上一次的 values」，将要渲染的文档是与 Release 存储中的值合并的结果，而 Server 不读 Release 存储——那次
校验只在 Agent 上做。

Chart 详情会连同 `values.schema.json` 原文一起返回，安装表单据此说明「提交前会按它校验」。没有打包 schema 的
Chart 不会被校验，也不因此多花任何开销。

## 缓存

仓库发布了什么，Server 存在自己的磁盘上。没有这层，每翻一页目录、每打开一个 Chart 都是一次对仓库的请求；进程
一重启全部丢光；仓库慢，Console 就慢；仓库读不到，目录就是空的——而这些 Chart 可能几分钟前刚读过，此后一个字
都没变。

目录结构沿用 Helm 自己的缓存，因为那是运维已经知道怎么读、怎么清的形状：

```text
data/helm/<repository-id>/index.yaml              索引原文
data/helm/<repository-id>/index.json              读到的时间与校验器（ETag / Last-Modified）
data/helm/<repository-id>/charts/<name>-<version>-<hash>.tgz
data/helm/<repository-id>/charts/<name>-<version>-<hash>.tgz.json
data/helm/<repository-id>/charts/<name>-<version>-<hash>.tgz.prov
```

`.prov` 与归档同名并列，正是 `helm pull --prov` 写出来的样子；它随归档一起写入、一起淘汰、一起删除——一份签署
某个摘要的文档，在它旁边的字节变了之后就是错的。

按仓库 **ID** 分目录而不是按名字：名字可以改、折叠大小写后可能撞车、而且是人取的；ID 在这条目录条目的整个生命
周期里不变，而那正好就是它下面这些文件的生命周期。文件名里的名字与版本是给人看的，真正做区分的是后面那段哈希
——Chart 名来自仓库的索引，Server 没有理由把它当作可信的路径片段。

它和 `data/pki` 一样是 `0700`，一样应该挂在 PV 上；但和 PKI 不同，**这里没有一个字节是权威的**：随时可以整个
删掉，下次再取回来。

两半的生命周期不同，因为它们的性质不同：

- **索引会变，所以会过期。** 默认 1 小时（`helm.cache.index_ttl`）。**这个 TTL 不是「磁盘副本保留多久」**——
  磁盘上的那份一直留到仓库被修改或删除为止；它只是「多久去问一次仓库变了没有」这个窗口。过期不等于重新下载：
  Server 带着上次拿到的 `ETag` / `Last-Modified` 发一次条件请求，没有变化的仓库回一个 304、不带正文，内存里
  那份解析结果继续用——对一份几十 MB 的公开索引来说，这是几百字节和「几十 MB 下载 + 重新解析」的差别。304 之后
  确认时间会写回磁盘，否则下一个请求又会再问一次，一个永远不变的仓库就会在每个 TTL 边界上被问到底。

  默认取 1 小时而不是几分钟，是因为短窗口买到的东西很少而花掉的不少：仓库发布 Chart 本来就不频繁，刚发布完的
  人手边就有「重新拉取索引」；而窗口越短，每个浏览会话向每个仓库发的请求就越多，遇上不带 `ETag` 也不带
  `Last-Modified` 的仓库，那还是一次完整的索引下载。要让新发布的 Chart 不点按钮就出现，就把它调短。
- **Chart 包不会变，所以不过期。** 一个已发布的版本就是一份确定的内容，留着直到需要腾地方为止（`max_bytes`，
  超出后按最近使用时间淘汰最旧的；索引不计入也不淘汰——它小，而且它正是「仓库读不到时目录还在」的那个东西）。
  取用之前一定校验：sidecar 里记着写进去时的 digest 和大小，而索引里那一条 `digest` 是仓库自己对这个版本的说法。
  两者中任何一个对不上都当作没有命中并删掉重取——这份归档接下来就要交给 Agent 应用到集群，半个文件和被改过的
  文件都不该走到那一步。OCI 那条路径本来就按 manifest 的 digest 校验，两边因此是一致的。

**仓库读不到时，目录降级而不是清空。** Server 返回磁盘上的那份副本，并在响应里置 `stale`，界面直接说明「以下是
上次读到的副本」。这一句是必须的：不说，「Chart 不见了」和「这份列表是上周的」在界面上完全一样。

**「重新拉取索引」**（`POST .../repositories/{id}/index-refresh`）是显式重读的入口，它**无条件**重新拉取——不带
`If-None-Match`，因为按这个按钮的人正是在说不信任手上这份，而条件请求会让仓库回 304 并原样把它留下。它不改变
任何存储状态，也不丢弃已缓存的 Chart 包（版本的内容不会变，重读索引问的是「有哪些版本」），所以要求的是
`helm.repository.read` 而不是管理权限。

**删除仓库会删掉它的整个缓存目录**——再没有任何东西能解释这些文件还留在盘上。

**修改仓库则要看改的是什么。** 只有改变「从哪里读、以什么身份读、读到的东西要证明什么」的编辑才作废缓存：
地址、用户名、密码（提交了就算改，因为存下来的那份永远不回读，Server 无从比较）、CA 证书、跳过 TLS 校验、
签名策略与公钥环。改名字、改描述、临时停用则不作废——这些都不是仓库发布的内容的一部分。一律作废曾经更简单，
但它在一个方向上是错的：一份公开索引就有几十 MB，它后面的归档更多，为了改一个错别字把这些全丢掉，会让下一个
打开目录的人替它重新下载一遍。判断是单向的：凡是这里判断不了的（包括读取旧记录本身失败），一律作废。

**Server 启动时核对并清扫一次缓存目录。** 它清的每一样东西都是「上一个进程没能善终」或「进程不在的时候有人动了
数据库」留下的残留，所以启动正是唯一需要做、也唯一能安全做这件事的时刻：

- 数据库里已经没有的仓库 ID，其目录直接清掉；
- **没写完的写入**。Chart 归档先写临时文件再改名，进程在这两步之间被杀掉，就留下一个和归档一样大、而这里其他
  机制都看不见的文件——它不是 `.tgz`，淘汰既不计它也不删它；它不是仓库目录，上一条也够不着它。不管的话，这就是
  一处针对缓存里最大那类文件的永久泄漏。判定按修改时间，阈值一小时：一个临时文件的存在时间是「创建到改名」之间
  的那点，一小时不是对写入耗时的估计，而是一个宽到任何在途写入都不可能落进去的余量；
- **归档已经不在的 sidecar**。它描述的东西没有了，不会再被读到，也没有别的机制会删它——淘汰只看归档。

清扫最后会应用一次容量上限。上限本来只在写入 Chart 时才应用，因此把 `max_bytes` 调小、或者进程死掉时缓存正好
超标，都会一直超到下一次下载为止；现在是启动时就回到限额以内。

一个安装或升级用的正是这份缓存：刚翻完文件就点安装，不应该把同一个包再下载一遍。以前这条路径刻意绕开缓存，因为
当时的缓存只是内存里一份没有校验的副本；现在它是按 digest 校验的，重用比重新下载更强——重新下载没有任何东西
保证拿到的还是同一个包。

缓存写失败从不导致请求失败：仓库仍然可达，答案仍然正确，只是回到了没有缓存时的开销。这类失败以 WARN 记录，
好让磁盘满或不可写这件事是看得见的。

### 磁盘前面还有一层内存

磁盘回答的是「要不要走网络」，内存回答的是「要不要再解析一遍」。一份几十 MB 的索引 YAML 解析出来的对象远不止
几十 MB，而在搜索框里每敲一个键都重解析一次，会让命中缓存和没命中一样慢。两份都是进程内的，不在副本之间共享：
里面的每一样东西都能从权威来源重新推出来，所以缓存更冷的副本只是更慢，不会更错。

两份都有上限，而且上限都不只是「装不下才丢」：

- **解析后的索引**最多 16 份，另外还有一个空闲上限——整整一个新鲜度窗口（`index_ttl`）里没人读过的索引会被
  释放。只按数量淘汰在只有三个仓库的平台上等于永不释放，而这里放着的正是本包持有的最大的对象；释放它的代价是
  下次从磁盘上那份重新解析一遍，永远不会变成一次对仓库的请求。
- **解析后的 Chart** 有 5 分钟的 TTL 和一个总字节预算。过期的条目在被查到时就地删除，淘汰时也先清过期再按最近
  使用时间清——一个过期条目永远不可能再被交出去，把预算花在它上面、还为它挤掉活着的条目，是把预算花在最不可能
  把它挣回来的那些条目上。

## Chart 文件浏览

`values.yaml` 与 README 说明一个 Chart 是做什么的，但它们不说明这个 Chart 会创建什么——那只写在模板里。
读不到模板的人会去别处下载这个归档，而那正是 ZKE 无从判断他们拿到了什么的地方。所以 Chart 详情页可以浏览
整个归档，内容就是仓库发布的那一份。

- **文件列表随 Chart 详情一并返回**。那个请求已经下载并解析了归档，再单独开一个接口取目录树，等于为了画一棵树
  把同一个归档下载两次。
- **文件内容按文件单独读取**（`GET .../charts/{chart}/file?path=…`）。一个带打包子 Chart 的归档可能有数百个
  文件，而读的人只会打开其中几个。
- 列表包含 `charts/` 下的子 Chart：安装一个 Chart 就是连同它的子 Chart 一起安装，藏起来等于藏起将要创建的
  大部分对象。界面默认把这棵子树折叠，而不是不列。
- `path` 与归档自身的成员名精确匹配，不做任何路径拼接，因此不存在可被穿越的路径。
- **是否文本按文件头部的字节判定，不看扩展名**：Chart 可以用任意名字打包任意内容，一个装着 gzip 流的 `.yaml`
  不应该被当成文本交给浏览器。非文本文件只报告存在与大小，不返回内容。
- 单个文件超过 512 KiB 会被截断并标注，`size` 仍是文件的真实长度；文件数超过 2000 时列表被截断并标注。
- 这是只读的。装进集群的是仓库发布的那个归档，唯一由操作者编辑的文档是 values，那发生在安装表单里。

浏览要求 `helm.repository.read`，与浏览 Chart 目录相同——它是同一份文档换一条路由，而不是新的一类访问。与
Chart 详情一样不写审计：没有暴露任何集群信息，而把每一次翻看模板都记下来只会淹没真正要看的事件。

为此 Server 把解析后的 Chart 在内存中留几分钟，归档本身则一直留在 `data/helm`（见上文）。没有这两层，点开一个
模板就是向仓库重新下载一次整个归档，翻十个文件就是十次。

## 一次变更的流程

在「Chart 目录」里选仓库、搜索、打开一个 Chart。这里能读到它自带的 `values.yaml` 原文、README、依赖的子
Chart、全部已发布版本、来源证明的校验结论，以及归档里的每一个文件。values 以文本原样返回而不是解析后的
对象——其中的注释就是一半的文档。

点「安装」之后是一个页面，它有三步，一次只呈现一步，后一步**替换**前一步：

| 步骤 | 内容                                                                                   |
| ---- | -------------------------------------------------------------------------------------- |
| 配置 | Chart 版本、Release 名、values 编辑器、执行方式开关。主操作只有一个：「预览并安装」     |
| 确认 | 集群渲染出的清单摆在最上面；下面是这次预览的过程与日志。可以「返回修改」或「确认安装」 |
| 执行 | 真正的写入，带着阶段、耗时与集群的日志；结束后报告修订号与 NOTES，或者失败的原因       |

这个形状是针对上一版的两个具体毛病定的。上一版有「预览」和「安装」两个按钮，两者的区别是操作者必须自己记住的
事；而预览渲染在一个长到看不见底的表单**下面**，常见的结果是按了「预览」、看着页面没变化、再按一次。现在只有
一个按钮，它推进页面，每一步都换掉上一步——预览不可能被错过，因为它就是当前这一步的全部内容。

「确认」不是装饰：`dry_run` 发出的是与提交**完全相同**的请求体，报告的是集群将会收到的清单，所以批准它就是
批准这个请求本身。安装展示清单本身，升级展示与当前修订的差异。返回修改会作废这份预览与它占用的幂等键——之后
提交的是另一个请求，用上一次的账目回答它会描述一份没人还在提交的配置。

升级同理，只是起点是正在运行的那个修订：它的 values 预填进编辑器，它的渲染清单成为差异的左侧。Helm 只记录
Release 用的是哪个 Chart，不记录它来自哪个仓库，所以升级时需要指明仓库。

「已安装应用」列表的每一行都直接带有升级、回滚与卸载：操作者在列表上已经知道自己要动哪一个，为了找到按钮先
进一次详情页，等于给每一次变更加一步而不回答任何新问题。确认对话框是同一批——安全边界不取决于从哪条路走到它。
行内的「回滚」目标是**上一个修订**（Helm 自己的默认），回到某一个指定的修订是对着历史做的决定，那仍然在详情页里；
第一个修订没有可以回去的地方，按钮不会出现。升级需要 Release 的 values，而列表只读 Secret 的标签（为四列表格
解压每一个 Release 是一页 Secret 的读取），所以那一行会在被点击时单独取一次它要的那个 Release。

回滚与卸载是对目标的决定而不是对内容的决定，因此是确认对话框而不是页面：

- **回滚**重放某次修订记录下来的对象，并写入一个新的修订——它不抹掉中间发生过的事。只能回到存储中仍然保留的
  修订：被 `--history-max` 清理掉的修订不再存在，界面也不会假装它们还在。
- **卸载**删除 Release 拥有的对象。`keep_history` 决定是否保留修订历史：保留下来的历史正是之后回滚所需要的，
  不保留则连同历史一并删除。

两个对话框在服务端受理之后就关闭，位置让给操作账目：它们要写的对象一样多、要等的时间一样长，而这段时间里
需要呈现的是过程而不是确认。

「已安装应用」列表顶部会列出**这个操作者自己**尚未结束的变更，并提供一个回到它账目的入口。窗口被关掉或刷新
之后，那次操作的身份只存在于那个页面的内存里，没有这个入口就再也找不回来了——操作照常执行，列表在下面悄悄
变化，日志却没有了。

## 权限

Helm 的写入是本 Server 上权限栈最长的一组路由，每一条回答的是同一个请求的不同问题。

| 操作                     | 需要的权限                                                                                                              |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| 浏览仓库、Chart 与其文件 | `helm.repository.read`（全局）                                                                                          |
| 管理仓库与其签名策略     | `helm.repository.manage`（全局）                                                                                        |
| 查看 Release 与 values   | `cluster.read` + `cluster.secret.read`                                                                                  |
| 安装 / 升级 / 回滚       | `cluster.read` + `cluster.helm.manage` + `cluster.resource.create` + `cluster.resource.update` + `cluster.secret.manage` |
| 卸载                     | `cluster.read` + `cluster.helm.manage` + `cluster.resource.delete` + `cluster.secret.manage`                            |

- `cluster.helm.manage` 说明「可以改 Release」，它单独不够：一次安装真正花掉的是对象的创建与更新权限，卸载花掉
  的是删除权限，持有 Helm 权限不会凭空变出写对象的能力。
- `cluster.secret.manage` 是必需的，因为 Helm 的 Release 存储**本身**就是一个 Secret，而它保存的 values 就是这个
  Secret 的内容。不能写 Secret 的角色不能写 Release。
- kube-\* 与 Agent 所在的命名空间照旧需要 `cluster.system_namespace.manage` 或 `cluster.agent_namespace.manage`：
  往 `kube-system` 装一个 Release 就是往 `kube-system` 写 Secret 和对象，路由叫什么名字不能成为绕过它的方式。

内置 `admin` 角色自动持有全部权限；内置 `viewer` 不含其中任何一项。

### Agent 侧的两条硬规则

权限判定发生在 Server，但有两件事只有渲染完成之后才知道，因此由 Agent 在写入之前对**实际渲染结果**判定：

1. **不得跨命名空间。** Server 授权的是一个命名空间。Chart 渲染出的对象若显式写着别的命名空间，Agent 指名拒绝
   （`helm_chart_cross_namespace`）。没有写命名空间的对象照旧落在 Release 的命名空间里，这是 Helm 自己的行为。
2. **集群级对象需要集群级授权。** CRD、ClusterRole、StorageClass 这类对象不属于任何命名空间，命名空间级的授权
   说明不了它们。只有持有该集群 `cluster.manage` 的操作者，请求里才会带上允许标记；否则 Agent 指名拒绝
   （`helm_chart_cluster_scoped`）。这个标记由 Server 从权限推出，请求正文里带这个字段会被直接拒绝。

界面会在没有 `cluster.manage` 时提前说明这一点，但判定始终在 Agent。

### Agent 的 Kubernetes 权限上限

Agent 在目标集群里的 ClusterRole 是一份显式清单，只覆盖 ZKE 自身功能涉及的资源类型。Chart 会创建它声明的任何
类型，因此**一个需要清单之外类型的 Chart 会被 Kubernetes 拒绝**，错误里指名是哪个类型——这是 Kubernetes 的
拒绝，不是 ZKE 的。

为此 Agent 绑定的 ClusterRole 是一个聚合角色：ZKE 自己的那份权限放在 `zke-agent-base` 里并带上聚合标签，集群
管理员可以创建自己的 ClusterRole、打上同一个标签来扩展它，Kubernetes 会把它们合并进来。

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: zke-agent-extra
  labels:
    zke.io/aggregate-to-agent: "true"
rules:
  - apiGroups: ["apiextensions.k8s.io"]
    resources: ["customresourcedefinitions"]
    verbs: ["create", "update", "patch", "delete"]
```

这样授权是集群管理员做出的、写在他们自己集群里的、`kubectl get clusterrole -l` 能看见的，也能在不重装 Agent
的情况下收回；ZKE 不会替他们决定发一份覆盖一切的权限。

## 审计

四种操作各有自己的动作，且预演与真正写入分开记录：

| 动作                                   | 何时写入                     |
| -------------------------------------- | ---------------------------- |
| `kubernetes_helm_release.install`      | 安装                         |
| `kubernetes_helm_release.upgrade`      | 升级                         |
| `kubernetes_helm_release.rollback`     | 回滚                         |
| `kubernetes_helm_release.uninstall`    | 卸载                         |
| 以上四个的 `.dry_run` 变体             | 预览                         |
| `helm_repository.create/update/delete` | 仓库目录变更（全局作用域）   |

四种操作不合并成一个动作，因为事后要问的正是「发生的是哪一种」：升级和回滚都产生一个新修订，含义却相反。
预览也记录，因为它确实在目标集群渲染了一次并读回了将要应用的清单；它不写入任何东西，把这两者分开正是分开记录
的意义。

审计写在**操作结束**的时候，记的是它的结果，而不是它被受理的时候。顺序上审计先落库、账目再宣布结束：账目是
调用方用来判断「做完了」的东西，而一件已经做完的事必须在有人能被这样告知之前就已经在审计里。请求在到达执行
之前就被拒绝（缺少确认、正文非法、无权判定集群级对象）同样记录，结果是 `failed`。

安装与升级的审计记录里还带上**装的是什么**：仓库 ID、Chart 名，以及请求指定的版本（不指定版本就如实记为空——
那正是一次没有钉住版本的请求）。目标名说明的是哪个 Release，而事后要问的往往是另一半：「这个 Release 是不是被
换到了一个没人批准过的仓库的 Chart 上」。解析后的实际版本在同一次操作返回的 Release 报告里。

审计目标名沿用 Secret 家族并附上 Release 名，这样按「谁改了这个命名空间的 Secret」筛选的人不会漏掉这条路径。
Release 的说明里会记下发起者，`helm history` 在 ZKE 之外也能读到。

## 重试与幂等

每次写入都带 `Idempotency-Key`。键由 Console 按**提交尝试**生成：一次预览和它之后的提交是两个请求，用两个键；
返回修改会开启新的一次尝试，因此也换一对新键。这两点都不是风格问题——它们各自对应一个具体的失败。

Server 按这个键认领它启动的操作：同一个键再来一次返回**已经在跑的那个操作**而不是再启动一个，这就是丢了 202
之后重试仍然安全的原因；同一个键用于另一个请求则拒绝为冲突（`409 idempotency_conflict`），因为用第一个操作的
账目去回答第二个请求，描述的是另一件事。

Agent 侧还有一层：它按这个键记住结果——同一个键、同一份请求重放上一次的答复，同一个键、不同的请求拒绝为冲突。
预览与提交的请求体只差 `dry_run` 一个字段，共用一个键正好落在「同一个键、不同的请求」上，这也是它们必须分开
的直接原因。

保留这个键是有代价的：键被占用之后，下一次用它的尝试会被判为冲突。因此只有**可能改变了集群**的结果才占用它。
预演不占用（它什么都没写，这也正是「先预览再提交」能共用同一个键的原因）；能够证明什么都没写的拒绝也不占用——
请求或正文被拒、集群根本连不上、Helm 在自己的存储上先行拒绝、以及渲染结果被 Agent 的两条硬规则拦下（post
renderer 在应用之前运行）。其余一律按「可能已经写入」处理：Helm 一旦开始应用，失败也可能留下对象，而 Agent
分不清这两种情况。

## 边界与限制

- 只支持 Secret 存储驱动。使用 ConfigMap 或 SQL 驱动的 Release 不会出现在列表里，也不能由这里管理。
- 来源证明只支持 Helm 自己的 PGP `.prov`。Sigstore / cosign 签名不在支持范围内。
- 校验只针对**归档整体**：摘要表里的容器镜像摘要（Helm 的 `images` 字段）不参与判断，ZKE 不代替镜像仓库回答
  镜像是什么。
- 单份 `.prov` 有大小上限（1 MiB），密钥环有大小与数量上限（256 KiB、64 把密钥）。
- **仓库地址**只支持 HTTP(S)：目录里录入的是一个能读到 `index.yaml` 的地址。把地址本身写成 `oci://`
  不受支持——镜像仓库没有索引，distribution 规范的 `_catalog` 是可选接口且主流公共 registry 并不开放，
  没有可以浏览的东西。**索引里的 `urls` 可以是 `oci://`**，那条路径是支持的，见上文。
- Chart 必须自带依赖（`charts/` 已打包）。ZKE 不会在安装时去解析和下载子 Chart，未打包依赖的 Chart 会被拒绝，
  而不是装出一个缺了一半的应用。
- 每个集群同一时刻只执行一个 Release 变更。两个并发操作会在 Helm 自己的存储上竞争，而 Helm 没有锁可以阻止
  它们；第二个操作会以 `helm_busy` 结束并提示稍后重试，而不是排队等待。
- 操作账目只存在于 Server 进程内，最多同时保留 64 份，结束 30 分钟后回收。回收是在这份登记表被用到时进行的
  ——启动一次新操作、读一次账目、或者某次操作结束——而不是由定时器驱动：始终成立的上限是那 64 份，30 分钟是
  一台还在干活的 Server 把内存还回去的时机。Server 重启会丢失账目：正在进行的操作仍然在集群里执行完，只是它的
  进度与日志没有了，结果要从 Release 列表和修订历史里看。
- 一次操作的等待时间有上限（默认 15 分钟，见 `agent_listener.helm_request_timeout` 与 Agent 的
  `connection.max_helm_stream_timeout`）。
- 渲染出的清单超过上限时会被截断并明确标注；提交本身不受影响。
